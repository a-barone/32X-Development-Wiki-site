Longword alignment and pipeline spacing

The SH-2 fetches instructions from its cache two at a time, and a data access that falls in the same pipeline step as a real fetch makes that step slower. Placing memory-access instructions on 4-byte boundaries, and spacing certain instruction pairs apart, avoids those delays. This page explains the rules, the one hardware measurement, and the traps. Use it when you write or tune SH-2 assembly for hot loops.

Summary#

  • Fetching. Code running from the cache is fetched 32 bits, two instructions, at a time. The second fetch makes no bus cycleDOC[S005-32]DOC[S005-2ins].
  • Alignment. A data access (MA) in the same slot as a free fetch does not split the slot. An MA against a real fetch doesDOC[S005-nosplit]DOC[S005-split]. So put instructions that access memory at longword boundariesDOC[S005-guide1].
  • A programming FAQ says the same. Toshiyasu Morita's "Programming the 32x FAQ", copied on the "Optimizations" page of the 32XDK wiki (the community-written wiki for 32X developers on GitHub), speaks of "a free bus access cycle on every longword instruction"COMM[S010-long].
  • Spacing. Keep multiply instructions apart, and do not use a loaded register in the very next instructionDOC[S005-guide3]DOC[S005-guide2].
  • Measured gain: 4 to 8% on a real PAL 32X. In the GenDev forum thread "Contention Between Instruction Fetch and Memory Access" (2021), the forum member ob1 moved one loop between a 4n and a 4n+2 address, which changed how its fetch and data access contendHW[S072-res].

Details#

The SH-2 has a five-stage pipeline: IF (fetch), ID (decode), EX (execute), MA (memory access) and WB (write back). The rules below are Hitachi's, from the pipeline chapter (section 7) of the SH-2 programming manual. Hitachi calls the time in which a single stage operates a slotDOC[S005-slot].

What the source claims#

Morita's FAQ says: "The SH2 has a free bus access cycle on every longword instruction".

  • So align memory reads and writes on longword boundariesCOMM[S010-long].
  • Put register-to-register operations between multiply-and-accumulate instructionsCOMM[S010-mac].

Mechanism#

  • From on-chip memory or the cache, the CPU fetches in 32-bit unitsDOC[S005-32].
  • Instructions are 16 bits, so one fetch brings two instructionsDOC[S005-2ins].
  • The fetch of the second instruction makes no bus cycleDOC[S005-nobus].
  • After a branch to a word boundary (address bits 1 and 0 = 10), the fetch brings only that instructionDOC[S005-word].
  • IF and MA both use memory, so they cannot run at onceDOC[S005-split].
  • A slot where they collide costs the MA's memory cycles plus the IF'sDOC[S005-sum].
  • A free fetch and an MA can share a slot without splitting itDOC[S005-nosplit].
  • Hitachi's advice: avoid MA and IF contention and pair MAs with free fetchesDOC[S005-pair].
  • Minimum cycle counts in the instruction tables grow when instruction fetch contends with data accessDOC[S004-cont].

Hitachi's programming guide (section 7.6) gives three rules:

  • Place instructions that have an MA stage so they start on longword boundariesDOC[S005-guide1].
  • The instruction right after a load must not use the load's destination registerDOC[S005-guide2].
  • Do not put multiplier instructions back to back, nor a MACH or MACL read right after a multiplier instructionDOC[S005-guide3]DOC[S005-mach].
  • Multiplier contention: an instruction that uses the multiplier after a MAC instruction waitsDOC[S005-macc].

Cost and conditions#

  • The free-fetch rule is stated for code in on-chip memory or the cache. On the 32X that means cached code, and the 32XDK wiki counts one cycle per instruction only for code that is cached and makes no outside accessesDOC[S005-32]COMM[S011-cached].
  • Padding for alignment must be NOPs. The SH-2 NOP is 0x0009, .align pads with zeros and .align 2, 9 gives 0x0909, both invalidCOMM[S010-nop]COMM[S010-0909].
  • GNU as .p2alignw pads with a chosen fill value (.p2alignw 2, 0x0009 fills with the NOP 0x0009), which the FAQ gives as the working fixCOMM[S010-p2].

Measured gain#

ob1 measured this on a real PAL 32X and posted it in the "Contention Between Instruction Fetch and Memory Access" thread:

  • One loop was placed at an address 4n and then at 4n+2. This tests the fetch of its last instruction against the memory access of its firstHW[S072-test].
  • The contention slowed the code by 4 to 8%HW[S072-res].
  • The loop sat inside an outer loop, so the figure variesHW[S072-pal].

ob1 does not say which of the two placements was the slower one.

A shipped example#

d32xr, the GitHub source of Doom 32X Resurrection, aligns its hand-written support routines, starting fast_memcpy after an .align 4 directiveCODE[S096-al]. The routine moves longwords (mov.l)CODE[S096-al].

Code example#

Example: a small hot loop that adds r0 longwords from the address in r1 into r3. The code is SH-2 assembly for GNU as. The point is only where the loop starts in memory. ob1 measured his own loop, not this one; the listing shows what the alignment directive does. The cost it avoids is the fetch and data-access collision described under Mechanism.

Before: nothing fixes the start address, so the loop can land on 4n+2.

loop:                           ! may start at any even address
        mov.l   @r1+,r2         ! r2 = next longword, r1 += 4
        dt      r0              ! r0 -= 1; T = 1 when it reaches zero
        add     r2,r3           ! r3 += r2; dt sits between load and use
        bf      loop            ! ADD leaves T alone, so this tests DT

After: a directive pads with NOPs until the loop starts on a longword boundary, as the 32XDK wiki's FAQ advises.

        .p2alignw 2, 0x0009     ! pad to a 4-byte boundary with NOPs (0x0009)
loop:                           ! now the loop starts at 4n
        mov.l   @r1+,r2         ! r2 = next longword, r1 += 4
        dt      r0              ! r0 -= 1; T = 1 when it reaches zero
        add     r2,r3           ! r3 += r2; dt sits between load and use
        bf      loop            ! ADD leaves T alone, so this tests DT

Notice that only the padding line differs. It costs a NOP or two once, outside the loop, and it can pay back on every pass. Placing the loop at 4n follows Hitachi's rule for instructions with an MA stageDOC[S005-guide1]. The dt sits between the load that fills r2 and the add that uses it, so the loop also keeps Hitachi's load-use ruleDOC[S005-guide2].

When it does not help#

  • Code that misses the cache: the free-fetch rule is for on-chip memory or cacheDOC[S005-32].
  • Loops dominated by slow external accesses (SDRAM bursts, cartridge, frame buffer), where the wait states dwarf one pipeline slot. See The SH-2 on the 32X for those costs.

Pitfalls#

A misaligned access is an address error, not a slow access. A word access must start at a 2n address and a longword access at a 4n addressDOC[S003-adrerr]. Align the data itself, not only the code.

  • Shipped start-up code points the CPU address-error vector at a handler. d32xr's master sends it to pri_errCODE[S096-adrvec].
  • Chilly Willy wrote in the GenDev forum thread "Notice on differences between emulator colors for 32x" (2012) that emulators ignore this. Misaligned code can pass on an emulator and crash on a real 32XCOMM[S170-odd2].

Tested on the jgenesis emulator#

These results come from the jgenesis emulator (version 0.14.1). Nobody has confirmed them on a real 32X yet.

  • A cached-read loop takes 8.00 clocks per pass whether its load starts at 4n+2 or at 4n. The emulator shows no alignment effect for cached codeEMU:jgenesis core 0.14.1[T400-a].
  • The register-only control loops also match at 4n+2 and 4nEMU:jgenesis core 0.14.1[T400-ac].

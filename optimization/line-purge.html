Selective cache-line purge

Each SH-2 caches memory reads, and the cache does not notice when the other CPU or a DMA changes the memory behind it. Before the reading CPU can trust cached data, the stale lines have to be thrown away, which is called a purge. This page explains how to purge only the lines that changed. Use it when one SH-2 reads data that the other CPU or a DMA wrote, and you want to refresh only the lines that changed.

Summary#

  • No snooping. The SH-2 cache does not snoop, so data another bus master changed must be purged from the reading CPU's cache before it is readDOC[S003-snoop].
  • One line at a time. An associative purge invalidates only the 16-byte line that holds one address: write a longword to that address plus $40000000DOC[S003-ap1][S003-ap40][S003-aplong].
  • When it pays. Hitachi calls it efficient when only a few lines changed. A large update is faster with a whole-cache purgeDOC[S003-eff][S003-whole].
  • Shipped use. d32xr, the GitHub source of Doom 32X Resurrection, purges only the lines it is about to read: its ring buffer between the two CPUs, and the object positions its sound code readsCODE[S171-rbline][S171-mo].

Details#

What the technique is#

Purge just the cache lines that hold data the other CPU (or DMA) wrote, right before reading them, instead of reading them cache-through or purging the whole cache.

  • Hitachi's cache chapter recommends it for a limited number of entriesDOC[S003-eff].
  • Hitachi's multiprocessor pattern keeps only the flags cache-through. The data itself stays cached and is purged before the first readDOC[S003-flags][S003-purge1st].

Mechanism#

  • The cache has no snoop function. Software keeps shared data coherentDOC[S003-snoop].
  • The associative purge space is H'40000000 to H'47FFFFFFDOC[S003-apspace].
  • A write to an address plus H'40000000 clears the valid bit of the line that holds that addressDOC[S003-ap40].
  • One purge write covers one 16-byte lineDOC[S003-ap1].
  • The four ways are checked at once. A line that is not cached is left aloneDOC[S003-ways].
  • A purge of 256 bytes of consecutive data takes 16 writesDOC[S003-ap256].
  • The purge write must be a longwordDOC[S003-aplong].
  • One line costs 2 cyclesDOC[S003-ap2c].

Cost and conditions#

  • Per line: one longword writeDOC[S003-aplong].
  • For 256 bytes: 16 writes x 2 cycles = 32 cyclesDERIVED[S003-ap256]DERIVED[S003-ap2c].
  • The other lines stay cached, so nothing else has to be fetched again. A whole-cache purge is the better choice only for a large updateDOC[S003-small]DOC[S003-whole].
  • The address written is the data's cached address plus $40000000. d32xr defines the base and adds the addressCODE[S171-assoc]CODE[S171-purge].

Measured gain#

Nobody has timed this on a real 32X yet.

Code example#

Example: after one CPU writes a shared buffer, the other CPU must purge the cache lines that hold it, or it will read stale data. The code is SH-2 assembly for GNU as. r3 holds the buffer's cached address and r2 the number of 16-byte lines. Purging a line means writing any longword to the line's address plus $40000000DOC[S003-ap40].

Before: purge the whole cache. CCR is the cache control register, and setting its CP bit clears every line. The routine below is d32xr's _CacheControl from crt0.s, which writes its argument to CCR; its comment names the bits as 0x10 = CP, 0x08 = TW and 0x01 = CECODE[S096-purgecc].

_CacheControl:
        mov.l   _sh2_cctl,r0    ! r0 = $FFFFFE92, the cache control register
        mov.b   r4,@r0          ! r4 = $11: CE = 1, CP = 1
        rts
        nop
_sh2_cctl:
        .long   0xFFFFFE92

After: purge only the lines of the buffer, 16 writes for 256 bytes.

        mov.l   purge,r0        ! r0 = $40000000, the associative purge space
        mov     #0,r1           ! r1 = the data written (its value is ignored)
loop:   mov.l   r1,@(r0,r3)     ! longword write to r0 + r3 purges that line
        dt      r2              ! one line done: r2 -= 1, T = 1 at zero
        bf/s    loop            ! more lines left: repeat
        add     #16,r3          ! slot: r3 moves to the next 16-byte line
        ...                     ! the buffer now reads fresh through the cache
        .align  2
purge:  .long   0x40000000

Notice that only the buffer's 16 lines are purged and every other line stays cached; the cycle cost is under Cost and conditions. The pointer increment sits in the delay slot of bf/s, as described on Fill the branch delay slots.

When it does not help#

  • A large update. Hitachi says purging the whole cache is then faster than purging every address in turnDOC[S003-whole].
  • Data read once and never again. Reading it cache-through avoids the purge, at the cost of a burst per access (see The SH-2 on the 32X).

Pitfalls#

A buffer that does not start on a line boundary keeps one stale line. A purge covers one 16-byte line, so such a buffer needs one line more than its length. Purge one extra line.

  • Each associative purge write invalidates one 16-byte lineDOC[S003-ap1].
  • d32xr's ring buffer purges (wcnt*2+31)/16 lines for wcnt wordsCODE[S171-nl].
  • That is the lines the bytes fill, plus one, so a buffer that starts anywhere inside a line is covered: (2 x wcnt + 31) / 16 = ceil(2 x wcnt / 16) + 1 in integer divisionDERIVED[S171-nl].

For a large update, purge the whole cache instead. Hitachi purges specific addresses for a small update and the whole cache for a larger oneDOC[S003-small][S003-whole]. d32xr purges its whole cache after it switches a ROM bank pageCODE[S096-bankcc].

Disable the cache before a whole-cache purge. Hitachi says to clear CE first, then purgeDOC[S003-ceoff]. d32xr's whole-cache purge turns the cache off, then purges and turns it back onCODE[S171-cc].

Purge with a longword store, not a byte or a word. Hitachi specifies longword access for associative purgesDOC[S003-aplong]. d32xr writes it through an unsigned long pointerCODE[S171-purge].

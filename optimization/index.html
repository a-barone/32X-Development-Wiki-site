Optimization techniques

This page is the entry point to the speed and size techniques known for the 32X. It sorts them by what you want to achieve, says in one line what each one buys and how well it is backed, and links to the page that explains it. Each technique page gives the mechanism, the cost, an example and the cases where it does not help.

Summary#

  • Most techniques come from one FAQ. Toshiyasu Morita's "Programming the 32x FAQ" opens the "Optimizations" page of the 32XDK wiki, the community-written wiki for 32X developers on GitHubCOMM[S010-faq].
  • Other sources. d32xr, the GitHub source of Doom 32X Resurrection, adds techniques from its code. CyberWarriorX's blog post "SH2 assembly optimizations" (2016) gives code-size tricks. Chibi Aliens, an SH-2 assembly tutorial site in the ChibiAkumas series, Hitachi's SH7604 manual and forum threads give the rest.
  • One gain is measured on a real 32X. In the GenDev forum thread "Contention Between Instruction Fetch and Memory Access" (2021), the forum member ob1 moved one loop from a 4n address to 4n+2 on a PAL consoleHW[S072-pos]. Collisions between instruction fetch and data access slowed it by 4 to 8%HW[S072-res].
  • Sharing the bus has a measured cost. In his GenDev thread "Concurrency penalty" (2021), ob1 ran the same loop of frame-buffer writes and SDRAM reads on both SH-2s. The slave ran 6 to 10% slower, on a real PAL 32XHW[S071-610]HW[S071-hw].
  • The FAQ's own grouping. It sorts its techniques into CPU work, bus bandwidth, salvaged waiting time and special hardwareCOMM[S010-types]. The table below groups by the goal instead.

Details#

Start with these three#

The first three techniques to try take work off the cartridge and the frame buffer, two slow memories (see the costs below). Each is backed by Sega's manual, the FAQ or working code.

  • Move the 68000 off the cartridge. The FAQ says 68000 code running in ROM "can seriously bring a 32x to its knees"COMM[S010-knees]. See Keep the 68000 off the cartridge.
  • Copy data the SH-2s read often from ROM into SDRAM. Sega's manual says an SH-2 regains speed by reading cartridge data after it has been loaded into SDRAMDOC[S001-sdram2]. d32xr's texture cache does this; see Cache textures from ROM in SDRAM.
  • Write two pixels at a time. In 256-colour mode, the FAQ says to collect at least two pixels in a register and write a word or longwordCOMM[S010-pix]. See Wide frame-buffer writes.

Time each change in your own loop before you keep it.

What each memory costs#

bakemono, a member of the Sega-16 forum, measured the cost of each memory in the thread "busting 32x performance myths" (2019). These costs explain why the bus techniques come first.

  • Cartridge ROM reads take 8 cycles per wordCOMM[S025-rom].
  • Frame-buffer writes take 5 cycles per word once the FIFO is fullCOMM[S025-fb].
  • Every SDRAM access is a 12-cycle burstCOMM[S025-burst].

The full table of wait states is on The SH-2 on the 32X.

"FAQ advice" means the technique is recommended but nobody has published its gain on a console. Emulator results are in their own section below.

Two d32xr commits from 2021 are correctness fixes, not speed-ups. One moves the V-blank tick counter from the 68000 to the master SH-2, because the old version "was prone to race conditions"CODE[S033-race]. The other reads the shared counter through the cache-through addressCODE[S032-alias2]. Both are on Dual-CPU synchronisation on the 32X.

Pitfalls#

A technique the FAQ calls faster can gain nothing in your loop. Each technique page states the conditions it needs. Time the change in your own code before keeping it.

Tested on the jgenesis emulator#

Test ROMs on the jgenesis emulator (core version 0.14.1) measured ten of these techniques. Nobody has confirmed them on a real 32X yet. One line per page; the details are on each page.

  • Wide frame-buffer writes: word writes halve the cost per pixel byteEMU:jgenesis core 0.14.1[T302-ab04].
  • Fill the branch delay slots: a filled slot saves one clock per taken branchEMU:jgenesis core 0.14.1[T400-ab07].
  • Smaller SH-2 code with immediates: a word constant built with mov #imm costs one clock more than a literal loadEMU:jgenesis core 0.14.1[T401-ab08].
  • Packed RGB maths and colour look-ups: 7.00 against 39.00 clocks per pixelEMU:jgenesis core 0.14.1[T401-ab10].
  • Cache textures from ROM in SDRAM: 7.25 against 14.00 clocks per wordEMU:jgenesis core 0.14.1[T404-gain].
  • Keep the 68000 off the cartridge: no difference, because the emulator does not slow SH-2 cartridge readsEMU:jgenesis core 0.14.1[T302-ab01].
  • Longword alignment and pipeline spacing: no difference for cached codeEMU:jgenesis core 0.14.1[T400-ab05].
  • Batch small writes in the SH-2 on-chip RAM: slower, 11 against 8 clocks per valueEMU:jgenesis core 0.14.1[T305-ab02].
  • SH-2 DMA in 16-byte mode: no faster than longword unitsEMU:jgenesis core 0.14.1[T303-ab03].
  • Overlap division with other work: no gain, because the emulator does not model the divider's timeEMU:jgenesis core 0.14.1[T400-ab11].

Dual-CPU synchronisation on the 32X

The 32X has two SH-2 processors, and a program only gains speed from them if they cooperate: one hands work to the other, they exchange commands, and they agree on who may touch shared data. This page describes the channels between the master and the slave, the rules for keeping their caches coherent, and the patterns that released code uses. Clocks, cache registers and wait states are on The SH-2 on the 32X.

Summary#

  • No shared view of memory. The two SH-2s share one bus and the SDRAM, but nothing merges their cachesDOC[S005-nomerge]. Shared memory must be read cache-through, or purged by the reading CPU after the other one changes itDOC[S005-coh].
  • Three channels. Sega's manual names three channels between master and slave: the serial linkDOC[S005-sci], the SDRAMDOC[S005-sdram], and the communication portsDOC[S005-cpfast].
  • Communication ports. They are eight words, fast to poll even cache-through, and shared with the 68000DOC[S005-cpfast]DOC[S005-cp8].
  • SDRAM carries bulk data, but it works in 16-byte units and the manual calls it unsuitable for flag pollingDOC[S005-16b]DOC[S005-flag].
  • Semaphores. Hitachi's semaphore recipe uses the TAS instructionDOC[S003-tasrec]. Sega forbids TAS on the 32XDOC[S001-tas].

The SCI receive interrupt is the only SH-2-to-SH-2 interrupt path any source names. TascoDLX, a member of the GenDev forum, describes its use in the thread "Mars Check Program results for Kega Fusion v3.61" (2009):

  • In the X-Men prototype the master uses the SCI to trigger an interrupt on the slave, with no useful data sentCOMM[S115-xmen]COMM[S115-nodata].
  • Sega's Mars Check test program exercises the SCI between the SH-2s in asynchronous mode at about 180,000 bits per second, which TascoDLX calls the maximum async rateCOMM[S115-async].
  • Kega Fusion 3.61 did not appear to emulate the SCICOMM[S115-fus].

Communication ports (SH-2 side)#

The ports are covered in full on Communication ports. The points that matter between two SH-2s are these.

ItemValueSource
addresses (cache-through)$20004020, $20004022, $20004024 and on to $2000402E, eight words, byte or word accessDOC[S001-cpaddr1]DOC[S001-cpaddr2]
simultaneous writesif the 68000 and an SH-2 write the same port at once, or one writes while the other reads, the value is undefinedDOC[S001-undef1]DOC[S001-undef2]
the manual's conclusion"dividing the register to be used as SH2 → 68000 and 68000 → SH2 must be avoided"DOC[S001-divide]

The 68000-side addresses and the port register itself are on Memory map.

Shipped code shares one port between the two SH-2s by taking turns.

  • d32xr, the GitHub source of Doom 32X Resurrection, a homebrew rework of Doom for the 32X, has its master SH-2 write a command to one portCODE[S194-cmd].
  • The slave writes it back to 0 when the command is doneCODE[S096-clr0]CODE[S096-poll].
  • That is a handshake with one writer at a time, so it never meets the case of master and slave writing at once.

d32xr names the ports by byte offset: COMM4 is the third word, at $20004024, and COMM6 the fourth, at $20004026CODE[S171-comm4]CODE[S087-comm6].

Keeping shared data coherent#

A cache is coherent when every CPU sees the latest value. The SH7604 cache does not snoop, which means it never watches the bus for writes by othersDOC[S003-snoop2]. Hitachi gives three ways to keep shared data coherent.

MethodHowWhen it paysSource
cache-throughput shared data in the cache-through area, so it never enters the cachesimple; slow if the data is read often and rarely rewrittenDOC[S003-ct]DOC[S003-slow]
break interruptthe user break controller raises an interrupt on a write to the shared area, and the handler purgesunpredictable, rare updatesDOC[S003-ubc]
purge by program logiconly the ready and done flags live in the cache-through area; the data itself stays cached and the reader purges before its first readbulk data handed over at known pointsDOC[S003-flags]DOC[S003-purge1st]
  • The writer has nothing to flush. The cache is write-through, so every write reaches memoryDOC[S003-wt2]. Only the reader's stale lines matter.
  • Purge a line by writing to its address plus $40000000.
    • The 32X manual's example: the slave writes to $46001004 after the master changed $06001004DOC[S005-ex1]DOC[S005-ex2].
    • d32xr's headers wrap this as a macro. It writes 0 to the purge-area address plus the line's addressCODE[S171-purge]CODE[S171-assoc].
  • Small update, purge the lines; large update, purge the whole cache. The latter is faster than purging every address in turnDOC[S003-whole].

Sharing the bus#

  • The slave has no bus normally and requests it for each external accessDOC[S005-slv2].
  • Cache reads need no bus, so a CPU reading from its cache does not wait for the other. Every CPU write still makes an external bus cycle (write-through)DOC[S003-par2]DOC[S003-wext2].
  • Two CPUs do not double throughput. The manual asks for a split of functions, or bus control, that cuts contentionDOC[S005-dbl2]DOC[S005-frag].
  • Handing the bus from one SH-2 to the other is reported to cost 2 to 3 clocksCOMM[S010-hand].
  • Toshiyasu Morita's "Programming the 32x FAQ", copied on the "Optimizations" page of the 32XDK wiki (the community-written wiki for 32X developers on GitHub), reports the bus-contention penalty as about 6 to 10%COMM[S010-610].
    • The FAQ links that figure to "Concurrency penalty" (2021), a GenDev forum thread started by the forum member ob1. ob1 ran the same loop of frame-buffer writes and SDRAM reads on both SH-2s, and the slave ran 6 to 10% slower, tested on a real PAL 32XHW[S071-610]HW[S071-hw]HW[S071-loop].
  • The same FAQ suggests collecting many small writes in the on-chip RAM (two-way cache mode) and writing them to SDRAM as one blockCOMM[S010-accum].
  • If both SH-2s run auto-request DMA at once, one side's DMA runs very slowly until the other finishesDOC[S001-dma3].

Start-up handshake#

  • Boot words. At boot the master writes "M_OK" at the start of the communication portsDOC[S001-mok]. The slave writes "S_OK" into the 2nd and 3rd wordsDOC[S001-sok].
  • The Mega Drive side must clear them when it moves on to the application. The SH-2 side waits until they are clearedDOC[S001-clr]DOC[S001-wait].
  • The CMD interrupt clear register and CMD mask bit exist once per CPU, at the same address on bothDOC[S001-cmdsep].

A shipped example: d32xr#

Doom 32X Resurrection (d32xr) uses both SH-2s for threaded renderingCODE[S059-both]. Its current source does the following.

PatternWhat the code doesSource
command loop on the slavethe secondary SH-2 spins reading one communication port until a command appears, then dispatches itCODE[S096-poll]
rendering splitslave commands include wall preparation, drawing planes and drawing spritesCODE[S096-cmds]
cache coherency by commandone command makes the slave clear its own cache; the master clears its cache and asks the slave to do the sameCODE[S096-cc]CODE[S096-both2]
per-CPU globalsthe slave points GBR at its own thread-local storage when it startsCODE[S096-tls]

Two earlier d32xr commits (2021) show the same thinking.

  • One moved the tick counter from the 68000 to the master SH-2's V interrupt. The 68000 version "was prone to race conditions" and the count sometimes went backwardsCODE[S033-race].
  • The old code read that count as one longword across two communication-port wordsCODE[S033-long].
  • Another commit read the counter through its cache-through alias, the variable's address OR 0x20000000CODE[S032-alias].
  • In the current d32xr, I_GetTime calls Mars_GetTicCount()CODE[S096-tic]. That macro reads the V-blank counter mars_vblank_count by name, without the cache-through aliasCODE[S171-tic].

This is Sega's advice in practice:

  • Small commands go through a communication port.
  • Bulk data goes in SDRAM.
  • The reading side purges, because nothing keeps the caches coherentDOC[S005-coh].

Pitfalls#

A TAS semaphore ported from Hitachi's recipe breaks Sega's rule. Build the lock from a communication port instead.

  • Hitachi says a TAS semaphore stays coherent without a purgeDOC[S003-tasrec], because TAS always goes to memoryDOC[S003-tasdir].
  • Sega's manual forbids TAS on the 32XDOC[S001-tas].
  • Sega's 32X Technical Bulletins are numbered notes from Sega's Developer Technical Support to 32X developers. The later Technical Bulletin 23 (29 November 1994) says TAS on the 32X always runs cache-throughDOC[S093-ct].
  • It slows code that repeats it on SDRAMDOC[S093-speed].
  • It keeps the other SH-2 off the bus from its read to its writeDOC[S093-bus].
  • Lusid Dreams, a SID music player for the 32X by mic on GitHub (2016), locks its sound mixer between the two SH-2s without TAS. It waits until the port COMM6 reads 1 (unlocked)CODE[S087-wait].
  • It then writes its own id there and reads it back, trying again when the other CPU wonCODE[S087-race]. The lock word is COMM6 at $20004026CODE[S087-comm6].

Polling a flag in SDRAM is expensive. A cache-through SDRAM read is always a full 8-word burstDOC[S001-ctb2].

  • The communication ports are the manual's fast place for flagsDOC[S005-cpfast].
  • d32xr's slave does its polling on a communication port, not in SDRAMCODE[S096-poll].

The communication port rule is written for the 68000 against an SH-2. The manual does not say whether the undefined-value rule also covers master and slave writing one port, so keep one writer per port at a time.

  • d32xr never lets the two SH-2s write one port word at the same time.
  • On COMM4 they take turns. The master waits until it reads MARS_SECCMD_NONE, the first command value, before writing a commandCODE[S194-wait]CODE[S194-none].
  • The slave writes 0 back when the command is doneCODE[S096-done].
  • On COMM6 the master changes only the high byte during wall preparation, by a byte store. Its comment lays out the word as (next seg)<<8 | last unready segCODE[S194-c6]CODE[S194-c6b].
  • That is Sega's byte-split rule for the 68000 and an SH-2, applied between the two SH-2s (see Communication ports).

The SCI has no external clock on the 32X. Configure the internal clockDOC[S005-sciclk].

  • Sega's Mars Check program keeps to this on both SH-2s. Each CPU's start-up code ends its SCI set-up by writing $70 to SCR (the serial control register)CODE[S196-m70]CODE[S196-s70], after SMR (the serial mode register) = $30CODE[S196-smr].
  • Decoded with Hitachi's bit tables: SMR bit 7 (C/A) = 0 selects asynchronous mode.
  • $70 = %01110000 sets RIE, TE and RE and leaves CKE1 = CKE0 = 0, the internal clockDERIVED[S003-ca0]DERIVED[S003-scrbits]DERIVED[S003-cke00].
  • Before that last write, with TE and RE still 0, the master writes $01 and the slave $03 to SCRCODE[S196-m01]CODE[S196-s03].
  • $03 = CKE1 + CKE0 set, the external-clock settingDERIVED[S003-cke1x]. It is held only while the SCI is off.

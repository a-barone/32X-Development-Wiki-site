The SH-2 on the 32X

The 32X carries two Hitachi SH-2 processors that share one bus and one memory map. This page covers their clocks, the master and slave roles, the cache, the cost of each memory region, and the rules Sega sets for them. Read it before you write SH-2 code. The same instruction can cost 1 clock or more than 12, depending on the memory it touches and on the cache.

Summary#

  • Two SH-2 CPUs share one bus. Sega's manual names the part SH7095DOC[S001-two][S001-7095].
  • Master and slave. The roles are fixed, and the master holds the bus by defaultDOC[S001-comp].
  • Clock speed. Each SH-2 runs at 23.01136 MHz on NTSC consoles and 22.801467 MHz on PAL onesCOMM[S011-clk]. Sega's manual sets the SH-2 clock period to one third of the 68000's, which gives the same figuresDOC[S001-sclk]DERIVED[S001-fosc].
  • Cache. Each SH-2 has its own 4 KB, 4-way, write-through cacheDOC[S003-81]DOC[S003-wt] with 16-byte linesDOC[S003-line]. Nothing keeps the two caches coherentDOC[S003-snoop].
  • Two addresses per region. Every region has a cached address and a cache-through address, which bypasses the cacheDOC[S003-same]. System and VDP registers must be accessed cache-throughDOC[S001-ct].
  • SDRAM. Every read is an 8-word burst of 12 clocksDOC[S001-sdr], even for one uncached wordDOC[S001-ctb]. Writes cost 2 clocks per wordDOC[S001-sdw].
  • Slow regions. A wait is one extra clock per access. Cartridge ROM costs 6 to 15 waitsDOC[S001-cart], frame-buffer reads 5 to 12DOC[S001-fbr], and the 32X system registers 1DOC[S001-sys].

Details#

Clocks#

The SH-2 clock is derived from the Mega Drive master clock, so it differs slightly between NTSC and PAL consoles. The table lists the figures; the derivation follows.

The SH-2 clock period is Sclk = Vclk/3 = 7 Mck/3, so the frequency is 3 times fosc divided by 7:

  • NTSC. 3 x 53.693175 / 7 = 23.01136 MHz.
  • PAL. 3 x 53.203424 / 7 = 22.801467 MHzDERIVED[S001-fosc].
  • Check. Both results equal the community figures in the first rows. The full clock chain is on Timings and clocks.

Clocks per wait state below are SH-2 clocks.

Cache#

Each SH-2 has its own cache, and nothing keeps the two coherent (see the pitfalls). The cache holds both instructions and data. It is split into ways: four independent banks, each with 64 entries, so that a given address can be stored in any of four places.

The cache control register#

The cache control register (CCR) is an on-chip register at $FFFFFE92. Its initial value is $00DOC[S003-ccr]. It has eight bits, 7 to 0: W1 W0 - CP TW OD ID CEDOC[S003-bits].

BitNameEffectSource
7-6W1, W0selects the way for direct address-array accessDOC[S003-w]
4CPwrite 1 to purge: clears every valid bit and all LRU bitsDOC[S003-cp]; the bit then returns to 0DOC[S003-cp1]
3TW0 = four-way cache, 1 = two-way cache plus 2 KB RAMDOC[S003-twb]
2OD1 = a data miss does not fill the cache (hits still read and update it)DOC[S003-od]
1ID1 = an instruction miss does not fill the cacheDOC[S003-id]
0CE1 = cache enabledDOC[S003-ce]

One sentence of the SH7604 manual says to write 0 to CP instead. d32xr, the GitHub source of Doom 32X Resurrection (a homebrew rework of Doom for the 32X), writes 1CODE[S096-cp11]; see Where sources disagree.

Change CCR only with the cache disabledDOC[S003-ccrdis]. The SH7604 manual gives the order for a full purge as: clear CE, then purgeDOC[S003-pord].

Address bits that choose the cache behaviour#

The top three address bits, A31 to A29, choose what an access does. The 32X's cache-through view ($2xxxxxxx, so A31-A29 = 001) is the cache-through partitionDERIVED[S003-p1].

Purging#

To purge one line, write to the line's address plus $40000000DOC[S003-ap]. Each write purges 16 bytesDOC[S003-ap16].

  • Example from the manual. When the master has changed $06001004, the slave purges its copy by writing to $46001004DOC[S005-ex1]DOC[S005-ex2].
  • In shipped code. d32xr ships the one-line purge as a macro. It writes 0 to the purge area ($40000000) plus the line's addressCODE[S171-purge]CODE[S171-assoc].
  • Whole cache. To purge everything, write 1 to CCR.CP. The 32X manual agreesDOC[S005-cp1]. See the disagreement section for the contradicting sentence.

Wait states per region (SH-2 side)#

A wait state is one extra clock that the CPU spends waiting for a slow device. A bus cycle takes at least 2 clocks on the SH-2 (4 on the 68000)DOC[S001-bus]. One wait adds one clock to that minimumDOC[S001-1w]. An access therefore costs 2 clocks plus its waits. The table gives the waits as the manual does.

  • Palette. The palette's long wait means one display line: when the CPU and the VDP compete for the palette, the CPU side waits a lineDOC[S001-pal64].
  • Other sources. Sega's 32X Hardware Information sheet (28 April 1994) gives the same SDRAM figuresDOC[S002-sdr] and the same cartridge waitsDOC[S002-cart]. The 32XDK wiki's table has the same valuesCOMM[S011-tbl].
  • Frame-buffer writes go through a 4-word FIFODOC[S001-fifo]. A write costs 5 clocks when the FIFO is full and 3 when it is notDOC[S001-fifo5]. The write figures assume back-to-back writes. Idle cycles between writes shorten the next one, but never below 3 clocksDOC[S001-idle].

Benchmarks by bakemono#

bakemono, a member of the Sega-16 forum, opened the thread "busting 32x performance myths" (May 2019) with memory timings from a test ROM of bakemono's own. The 32XDK wiki's "SH2 on the 32X" page lists the same conclusions, so each row below cites both.

How the test works, as bakemono describes it:

  • Each pass of the test loop reads four 32-bit words. A pass takes 11 cycles when every access hits the cacheCOMM[S025-11]COMM[S011-b6].
  • The "sparse" tests touch one 32-bit word every 16 bytesCOMM[S025-sparse].
  • The 68000 ran from RAM and did not touch the cartridgeCOMM[S025-68k].
  • The test ROM counts 30 V-blanks as half a second, so its figures are off on a PAL consoleCOMM[S025-rom].
Accessbakemono's resultSource
SDRAM, any accessalways a 12-cycle burstCOMM[S025-sdr]COMM[S011-b1]
frame-buffer writes ("VRAM" in the post)5 cycles per word once the FIFO is fullCOMM[S025-vram]COMM[S011-b2]
cartridge ROM8 cycles per wordCOMM[S025-rom8]COMM[S011-b3]
cartridge ROM through the cached viewa whole-line "burst", with no timing gainCOMM[S025-romc]COMM[S011-b5]
sequential SDRAM writesfast; random writes were not part of the testCOMM[S025-seqw]COMM[S011-b4]

The frame-buffer result matches the manual's 5 clocks for a write into a full FIFO (see Wait states above). The cartridge result equals the manual's best case: a 2-clock bus cycle plus the minimum of 6 waits is 8 clocksDERIVED[S001-cart8]. bakemono adds that the Kega Fusion emulator "does not emulate all of this timing nuance"COMM[S025-fus].

Chilly Willy, writing in 2011 in the SegaXtreme forum thread "Advanced Audio Compression on the 32X" while porting the Tremor Ogg Vorbis decoder, recalls the same cartridge figure: 8 cycles per word at bestCOMM[S053-rom]. He also describes the SH-2 as sitting on a 16-bit bus on the 32XCOMM[S053-16].

Tested on the jgenesis emulator#

These results come from the jgenesis emulator (version 0.14.1). Nobody has confirmed them on a real 32X yet.

  • Writing CP = 1 purges the cache; writing CP = 0 does notEMU:jgenesis core 0.14.1[T007-cp].
  • After a cache-through write, a cached read returned the stale value, so the emulator models the data cacheEMU:jgenesis core 0.14.1[T007-model].
  • CP reads back 0 after writing $11EMU:jgenesis core 0.14.1[T007-rb].
  • CCR reads $01 (CE = 1, cache enabled) at application entryEMU:jgenesis core 0.14.1[T007-ccr].
  • Both SH-2s enter the application with CCR = $01: cache on, OD and ID clearEMU:jgenesis core 0.14.1[T013-ccr].
    • CCR = $01 = 0000 0001 in binary, so the TW bit is 0, and TW = 0 means four-wayDERIVED[S003-twb].
  • A timing run measured one clock per register instruction and 11 clocks per cache-through SDRAM readEMU:jgenesis core 0.14.1[T302-c0]. The manual says 12 clocks for the burstDOC[S001-sdr].
  • The divider's time and its register-access cycles are not modelled: division reads cost what a register move costsEMU:jgenesis core 0.14.1[T400-vt2]. See SH-2 on-chip peripherals on the 32X.

Pitfalls#

An uncached SDRAM read of one word still costs the full 8-word, 12-clock burstDOC[S001-ctb]DOC[S001-sdr]. The 32XDK wiki calls it the slowest access an SH-2 can makeCOMM[S011-slow].

Cartridge ROM gives no burst.

  • The bus controller reads ROM as single accesses. Through the cached view a miss still fills a whole lineCOMM[S011-rom].
  • For sparse reads that is wasted work, so uncached sparse reads are fasterCOMM[S011-sparse].
  • For dense reads the line fill pays offCOMM[S011-dense].
  • d32xr copies its ROM data to SDRAM at resetCODE[S096-recopy]. It marks its block copy "runs from sdram for speed"CODE[S096-memcpy].

The SH-2 waits on cartridge ROM while RV = 1, until the 68000 clears itDOC[S001-rv].

  • When both CPUs read the ROM at once, the SH-2 goes firstDOC[S001-prio].
  • RV and FM belong to the system registers; see System registers.
  • d32xr works around it. Its SRAM functions make the 68000 set RV, so the program must not read ROM while they runCODE[S171-rv1]CODE[S171-rv2].
  • d32xr's master command interrupt handler does its waiting in SDRAMCODE[S096-cmdwait].

The SH-2 can touch the frame buffer, overwrite image, VDP registers and palette only while FM = 1DOC[S001-fm].

  • d32xr's master sets FM in its start-up code through the cache-through system-register addressCODE[S096-fm].
  • What an access does while FM = 0 (ignored, or stalled until FM = 1) is disputed inside the manual; see where sources disagree.

Sega forbids a short list of things on the 32X's SH-2. The list sits under "Precautions when using 32X SH2 (SH7095)". The manual does not guarantee what follows any of themDOC[S001-prec].

  • The TAS instructionDOC[S001-tas].
  • SLEEP in an applicationDOC[S001-sleep].
  • Touching the bus state controller at $FFFFFFE0-$FFFFFFFFDOC[S001-bsc].
  • A watchdog-timer internal resetDOC[S001-wdt].
  • The standby control register at $FFFFFE91DOC[S001-sbycr].
  • The master boot ROM uses two of them itself. In the GenDev forum thread "Master SH2 BIOS" (2007), the forum member ob1 posted a disassembly of that ROM. It shows the ROM writing $9F to SBYCR ($FFFFFE91) and then executing SLEEPCODE[S018-sby]CODE[S018-sleep].
  • In the GenDev thread "Using 32x as a 3rd plane, possible?" (2019), Chilly Willy instead suggests SLEEP to idle an SH-2, run from SDRAMCOMM[S044-sleep]COMM[S044-sdram]. This disagrees with Sega's rule; see where sources disagree.

The on-chip free-running timer (FRT) is not available to programsDOC[S001-frt].

  • It falls under the manual's interrupt restrictions. They apply to programs that use the 32X interrupts together with on-chip module interrupts.
  • The required FRT settings are on Interrupts and SH-2 on-chip peripherals on the 32X.
  • d32xr keeps to this. Its timing uses the watchdog timer, and its handler writes TOCR = $E2, Sega's FRT valueCODE[S096-tocr].

The caches do not snoopDOC[S003-snoop].

  • A write by the other SH-2 or by any other bus master can leave a stale line in this CPU's cache. The DMAC cannot write into the cacheDOC[S003-dmac].
  • What to do: read shared data through the cache-through view, or purge the lines first. Patterns are on Dual-CPU synchronisation on the 32X.
  • d32xr clears its own cache and then asks the slave to clear its cache by commandCODE[S096-ccboth].

Cache hits keep running while the other SH-2 holds the bus. The cache is on its own internal busDOC[S003-par]. Every write still makes an external bus cycle, because the cache is write-throughDOC[S003-wext].

A cache-line fill cannot be interrupted by a bus requestDOC[S003-nofill].

A word access at an odd address, or a longword access off a 4-byte boundary, is an address errorDOC[S003-adrerr].

  • In the GenDev thread "Notice on differences between emulator colors for 32x" (2012), Chilly Willy notes that emulators of the time let such accesses through. Code that worked there would have crashed on a real 32XCOMM[S170-odd2].
  • d32xr's start-up code routes the CPU address-error vector to its error handler pri_errCODE[S096-adrvec].

A cache-through SDRAM read wastes the other 12 bytes of the burst. The SH7604 manual makes the same pointDOC[S003-waste].

  • d32xr's ring buffer between the two CPUs reads its shared data through the cache. It purges each line before it reads itCODE[S171-rbline].
  • It reads only its two position words cache-throughCODE[S171-rbunc].

TAS always reads memory cache-throughDOC[S003-tas1]. It holds the bus from its read to its writeDOC[S003-tas2].

  • Sega forbids TAS on the 32X (see above).
  • Sega's 32X Technical Bulletin 23 (29 November 1994) says the same for the 32X: TAS always runs cache-throughDOC[S093-ct].
  • Repeated use on SDRAM slows codeDOC[S093-speed].
  • The bus cannot pass between the SH-2s during itDOC[S093-bus].
  • Lusid Dreams, a SID music player for the 32X by mic on GitHub, locks between the two SH-2s on the communication port COMM6 without TAS. It writes its own id and reads it back, trying again when the other CPU wonCODE[S087-race].

The SH7604 manual's cache-initialisation listing (figure 8.12) is wrong as printed.

  • The listing's last line writes the value to a register, not to CCRDOC[S003-lst]DOC[S005-lst].
  • What to do: program from the CCR table above, not from that listing.
  • Working code does it with a byte store of $10, then $11, to CCRCODE[S096-cp10]CODE[S096-cp11].

Two SH-2s running auto-request DMA at once slow each other down. One side's DMA runs very slowly until the other finishesDOC[S001-dma2]. Schedule the two CPUs' DMA transfers one after the other.

Where sources disagree#

Does writing 1 or 0 to CCR.CP purge the cache? Working code settles it.

  • The SH7604 manual's cache chapter says a purge happens when 1 is written to CPDOC[S003-cp]. Another sentence there says the same.
  • A later sentence says a full purge is done by writing 0 to CPDOC[S003-cp0]DOC[S005-cp0].
  • The 32X manual says write 1DOC[S005-cp1].
  • d32xr's start-up writes $10 (CP = 1, cache off), then $11 (CP = 1, cache on) to CCRCODE[S096-cp10]CODE[S096-cp11]CODE[S096-ccr].

Does an on-chip register access wait while the other SH-2 holds the bus?

  • The SH7604 manual says the CPU's internal bus to the on-chip modules runs in parallel with the external bus, unless the break controller's bus monitor is setDOC[S003-par2].
  • Sega's Technical Bulletin 32 says the access waits until the bus master is doneDOC[S080-wait]COMM[S011-io2w].

How long can an SH-2 cartridge access take?

  • The 32X manual gives 6 to 15 waits on a 2-clock minimum bus cycleDOC[S001-cart]DOC[S001-bus]. That is 8 to 17 clocksDERIVED[S001-cart8].
  • Later in the same Sega-16 thread, bakemono recalls the documentation allowing "from 8 up to 18 clocks"COMM[S025-818].

Open questions#

  • Is the SH7095 the same chip as the SH7604? The 32X manual names the part SH7095, while the 32XDK ships Hitachi's SH7604 manual.
  • Why does Sega forbid TAS on the 32X? The manual states the rule without a reason.
  • What does CCR hold on a real console when the application starts?
    • s32x-bios-disassembly, a GitHub project by the GitHub user SONIC3D that turns Sega's master and slave boot ROMs back into assembly source, shows each CPU writing $11 to CCRCODE[S191-ccr].
    • CP clears itself after the purgeDOC[S003-cp1], which would leave $11 minus CP ($10) = $01DERIVED[S003-cp1]. jgenesis reads that value (see the emulator section).

DMA (68000 to SH-2 FIFO, SH-2 DMAC)

This page covers the two ways a 32X moves bulk data without the CPU copying every word. One is the 68000-to-SH-2 transfer through a small hardware FIFO (first-in, first-out queue). The other is the DMA controller (DMAC) built into each SH-2. Read it before you move bulk data from the Mega Drive side into the 32X, or before you set up a DMA on an SH-2.

Summary#

  • One-way bulk path. The FIFO transfer is the only hardware path for bulk data from the Mega Drive side into the 32X. A 2009 claim of the reverse direction in the GenDev thread "Shared Memory" was withdrawn by its author, Chilly WillyCOMM[S022-oneway].
  • How it runs. The 68000 writes words into the 32X FIFO. The FIFO's DREQ0 line (DMA request) drives SH-2 DMAC channel 0, which copies the words into memoryDOC[S001-path][S001-dreq][S001-fifo68].
  • PWM. DMAC channel 1 can feed the PWM pulse width registers from memory on an external requestDOC[S005-ch1].
  • 68000 side. Set the length (in units of 4 words), set 68S, write words to $A15112, and check the FULL flag every 4 wordsDOC[S001-len4][S001-68s][S001-full4].
  • SH-2 side. Channel 0 reads from $20004012, with a transfer count equal to the DREQ length, on an edge-triggered external requestDOC[S001-sar0][S001-tcr0][S005-edge].
  • 68S going back to 0 only means the 68000 side is done. The SH-2 must report its own end, for example through a communication portDOC[SP1-68s][SP1-report].

Details#

Registers#

Four registers on the 68000 side and two on the SH-2 side take part. 68S is the bit that starts a transfer, and FULL is the flag that says the FIFO has no room.

Bit detail is on System registers. The DREQ source and destination address registers are not used by the DREQ circuitDOC[S001-src].

68000 side (CPU write)#

The 68000 pushes data into the FIFO by hand. The steps are:

  • Set the length register. It counts down once per transfer, and 0 means 65,536DOC[S001-lenset][S001-len0].
  • Set 68S (bit 2 of the DREQ control register) to 1 to startDOC[S001-68s].
  • Write each word to the FIFO, and write only while FULL (bit 7) is 0DOC[S005-fullrow][S005-full]. Check FULL every four words, because the SH-2 side may answer slower than a 68000 accessDOC[S001-full4][S001-full4why].
  • When the 68000 side has sent everything, 68S returns to 0 by itself and further FIFO writes are ignoredDOC[SP1-68s].

SH-2 side (DMAC channel 0)#

Each SH-2 has a DMA controller with channels 0 and 1. Section 5.3 of Sega's 32X Hardware Manual gives the settings below for a transfer from the FIFO to memory. SAR is the source address register, DAR the destination, TCR the transfer count, CHCR the channel control register, DRCR the request source register and DMAOR the operation register.

  • Request type. External requests must be edge-triggered, not level-triggered, in dual address modeDOC[S005-edge][S005-dual].
  • No acknowledge. The interface chip does not use DACK, the DMA acknowledge lineDOC[SP1-dack].
  • Register meanings. The SH7604 registers are explained on The SH-2 on the 32X.

Channel 1 to PWM, and memory to memory#

The same DMAC can feed the PWM FIFO from memory, or copy memory to memory.

The PWM request comes from the RTP bit of the PWM control register (see System registers). PWM use is described on PWM sound (registers, cycle, FIFO).

How the FIFO works#

Sega's Hardware Manual Supplement 1 (June 30, 1994), a correction sheet to the manual, describes the FIFO's inner workings:

  • It has two blocks, A and B, of 4 words eachDOC[SP1-ab].
  • The 68000 fills block A first, then block B, switching block each time one is fullDOC[SP1-ab].
  • When a block holds 4 words, the interface chip raises DREQ0 and the SH-2 DMA reads $20004012DOC[SP1-dreq]DOC[S001-r4012].
  • FIFO Full means the 68000's next block is the one the SH-2 is reading or about to readDOC[SP1-fullwhy].
  • Writing while the FIFO is full is undefinedDOC[SP1-over].

Stopping early#

Writing 0 to 68S during a transfer stops it:

  • The SH-2 DMA then sees DREQ0 forced low. What follows is undefined, including the FIFO's write counterDOC[SP1-force][SP1-undef].
  • Sega allows the forced stop only at VRES reset or when the 68000 controls the SH-2 sideDOC[SP1-vres].

Data loss on the FIFO path#

Chilly Willy and ob1, both GenDev forum members, reported lost data on this path when they used it on real hardware. Vic, who maintains d32xr (the GitHub source of Doom 32X Resurrection), later found a cause. All three posted in the GenDev forum thread "Super VDP", except ob1's 2021 test, which is in the thread "DMA DREQ delay".

What shipped games do#

SoullessSentinel, a member of the GenDev forum, posted a disassembly of Knuckles' Chaotix in the thread "68K to SH2 DMA FIFO" (2013). It shows working code from the time for this pathCODE[S020-src]. The sequence is:

SideStepSource
68000Interrupts off (SR = $2700).CODE[S020-sr]
68000Set 68S by writing #4 to -$B(a0), then set INTM (#1 to $A15103) to raise a CMD interrupt on the master.CODE[S020-68s]
68000Wait until INTM reads back 0.CODE[S020-intm]
68000Write four words to the FIFO with four move.w, then wait while FULL is set. Repeat.CODE[S020-full]
SH-2CMD handler: CHCR0 = $44E0 first (not 0), SAR0 = $20004012, then CHCR0 = $44E1.CODE[S020-44e0][S020-sar][S020-44e1]

The code keeps the FIFO address $A15112 in a0. So -$B(a0) addresses $A15112 - $B = $A15107, the byte that holds 68SDERIVED[S020-a0][S020-68s]. The FULL wait, tst.b -$B(a0) followed by bmi, tests bit 7 of that same byteDERIVED[S020-a0][S020-full].

  • Night Trap 32X. In Chilly Willy's reading of the code, it sends at most $400 bytes at a time and waits for the SH-2 to answer "GOOD" or "AGIN" in a communication registerCOMM[S020-nt][S020-good].
  • How common the path is. SoullessSentinel found $A15112 only in Chaotix, Primal Rage and Virtua Racing among the 32X games he hadCOMM[S020-few].
  • A different route. In 2013 Chilly Willy moved his data through the communication ports instead, up to 128 KBCOMM[S020-comm][S020-128].
  • Why. The FIFO DMA lost data on a real 32X while it worked in an emulatorHW[S020-hw].

Working code today#

Doom 32X Resurrection is a homebrew rework of Doom for the 32X, and its source, d32xr, is public on GitHub. Its 68000 and SH-2 transfer code does the following.

Pitfalls#

All 32X quirks are collected on Bugs and quirks.

The FIFO path can drop words on real hardware. Chilly Willy measured 20 to 120 words lost per 65,536 words sentHW[S036-rate]. In 2025 Vic tied it to how the TE bit of CHCR0 is clearedCOMM[S036-te].

Chilly Willy reports that Sega's CD-mode transfer path does not workCOMM[S036-cdmode].

FIFO writes need 68S set first.

  • On real hardware $A15112 is write-only from the 68000. The SH-2 side does not see words written while 68S is 0, and a 68000 read returns 0HW[S112-wo][S112-68s][S112-zero][S001-r5112].
  • The jgenesis emulator reproduces this; see the emulator test below.
  • What to do: set 68S to 1 before the first FIFO write.

FULL means both blocks are full.

  • TascoDLX, a GenDev forum member, posted the expected results of Sega's Mars Check test program in the GenDev forum thread "Mars Check Program results for Kega Fusion v3.61" (2009). The FIFO test expects "not full" at 7 of 8 words and "full" at 8 of 8COMM[S115-full].
  • The test's code says the same. After 7 FIFO words it requires FULL = 0, after the 8th FULL = 1, and FULL = 0 again once 68S is clearedCODE[S189-f7][S189-f8][S189-f0][S189-prac].

Some Mars Check DMA tests overwrite the program's own code.

  • TascoDLX, in the thread above, relays that the Mars Check tests have been reported to pass on real hardwareCOMM[S115-hw]. dilworks, commenting on issue #96 of the PicoDrive emulator's GitHub repository (2019), reports that they pass on a real consoleCOMM[S179-hw].
  • In that issue, notaz, the author of the PicoDrive emulator, says the test program overwrites its own code in some testsCOMM[S179-code]. It passes on real hardware only because that code stays in the SH-2 cacheCOMM[S179-cache].
  • TascoDLX reads the ROM-to-SDRAM and frame-to-SDRAM tests (tests 127, 128 and 133) as setting an illegal 16-byte transfer unitCOMM[S115-unit]. Snake, another forum member, answers in the same thread that no unit mode is illegal and all work as documentedCOMM[S115-snake]. Both are forum statements; see where sources disagree.
  • The ROM itself shows the oversize transfer. Its ROM-to-SDRAM parameter table holds destination $06020000 and count $8000. With the 16-byte unit its CHCR value selects, that is 524,288 bytes against 256 KB of SDRAMDERIVED[S235-der].
  • The bytes 06 02 00 00 00 00 80 00 occur four times in the ROMCODE[S235-found]. notaz's patch, which halves the count in them, is described on Test ROMs: Sega's Mars Check Program.

Do not write 0 to CHCR0 between transfers.

  • Shipped Chaotix writes $44E0 before $44E1CODE[S020-44e0][S020-44e1][S020-tap0][S020-tap1].
  • ob1 later suggested this pattern as the one difference he could spotCOMM[S036-hedge][S036-chcr].
  • d32xr clears TE the same way todayCODE[S088-te].

68S = 0 does not mean the SH-2 has the data. Report the end from the SH-2 through a communication portDOC[SP1-report]. The SH-2 side of d32xr waits for TE and then acknowledges in communication word 0CODE[S088-ack].

The DMA-end interrupt: one real-hardware test says no, shipped homebrew says yes.

  • In the GenDev forum thread "DMA DEI" (2021), ob1 set the interrupt-enable bit of CHCR ($44E5 instead of $44E1), a vector in VCRDMA and a handler address. ob1 reports it did not work on real PAL hardwareHW[S180-ob1][S180-44e5].
  • Chilly Willy's interrupt-driven DMA PWM example, posted in the GenDev thread "Interrupt driven DMA PWM audio" (2012), writes CHCR1 = $18E5 ("intr enabled") and runs its refill from the DMA-end handler. Chilly Willy says it works on real hardwareCODE[S183-18e5][S183-hw].
  • Vic replied in the "DMA DEI" thread (2024) that Chilly Willy's driver proves the bit worksCOMM[S180-vic]. The disagreement is open; see where sources disagree.

Leave time between setting 68S and the first FIFO write.

  • ob1 calls 11 NOPs "the bare minimal" and prefers about 100 cycles. ob1 suggests the delay "might be needed" for the DREQ circuit, and tested on Fusion 3.64 and GensKMod onlyEMU[S181-nops][S181-100][S181-might][S181-emu].
  • d32xr's 68000 transfer code does not rely on a delay. After setting 68S it waits for the SH-2's handshake in communication word 0 before the first FIFO writeCODE[S088-68s][S088-hs].

Development target Ver. 1.x: under $100 words per transfer. Sega's "32X Hardware Information" notes, part 2 item 10, set this limit; Ver. 2.0 has no such limitDOC[S002-v1][S002-v2].

Both SH-2s running DMA at once: one runs very slowly until the other finishesDOC[S001-both].

Auto-request DMA blocks PWM feeding and H-interrupt VDP access. Sega says not to use it when an SH-2 drives PWM or touches the VDP in its H interruptDOC[S001-auto].

  • Sega's Mars Check feeds PWM by DMA with CHCR1 = $18E1CODE[S200-chcr1].
  • In that value bit 9 (AR) is 0, which selects module request, not auto-request: ($18E1 >> 9) AND 1 = 0DERIVED[S200-chcr1][S005-ar].

A forced stop is undefined except at resetDOC[SP1-undef]. The forced stop Sega means is the 68000 ending a FIFO transfer by writing 0 to 68SDOC[SP1-force].

  • Sega's Mars Check program clears its SH-2 DMAC in its VRES (reset) handler. It writes 0 to DMAOR ($FFFFFFB0) and CHCR0 ($FFFFFF8C) before it restarts its start-up codeCODE[S211-vres]. That resets the SH-2 side only; it is not a 68S forced end.

Word-RAM-to-VRAM "capture" DMA with a Sega CD fetches undefined data. Sega's 32X Technical Bulletin 13 (September 1994) says soDOC[S147-wram], and the "Bugs and quirks" page of the 32XDK repository wiki repeats itCOMM[S009-wram].

Techniques#

Interrupt-driven DMA to PWM is covered on the audio pages DMA-driven PWM. Bus effects of two DMAs are on Bus arbitration.

Tested on the jgenesis emulator#

jgenesis is a Mega Drive and 32X emulator whose source is on GitHub. These results come from its version 0.14.1. Nobody has confirmed them on a real 32X yet.

  • With 68S = 0, a 68000 read of $A15112 returns $0000 and two SH-2 reads of $20004012 return $0000, which is what the hardware report describes for a real consoleEMU:jgenesis core 0.14.1[T025-68k][T025-sh2][T025-rows][T025-res].

Where sources disagree#

  • Does the SH-2 DMA-end interrupt (the interrupt-enable bit of CHCR) fire on a real 32X? ob1's real-PAL test says no. Vic points to Chilly Willy's interrupt-driven PWM sound driver as proof that it does.
  • Is the SH-2 DMAC's 16-byte transfer unit legal on the 32X? TascoDLX and Snake disagree, both in forum posts.
    • Sega's own Mars Check frame-buffer DMA routines also use the 16-byte unit, in auto-request modeCODE[S205-unit].

Open questions#

  • Do the FULL and EMPTY bits of the SH-2 DREQ control register follow the frame buffer write FIFO, as Sega's sample code names them? See System registers.
  • How many bytes does one SH-2 DMA with the 16-byte unit move for a given transfer count on a real 32X? A test case for this would also settle the 16-byte unit question.
    • Near develops the ares emulator and posted about its 32X emulation in the GenDev forum thread "Questions on emulating the 32X" (2021). He reports that all 161 Mars Check tests pass once ares decrements TCR by 4 per transfer in 16-byte modeEMU[S172-tcr].
  • How many words does the FIFO path lose over 65,536 words, with the old TE-clear sequence and with the new one? The loss shows only on real hardware.

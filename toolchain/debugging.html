Debugging (GDB remote stubs for the SH-2)

Debugging SH-2 code on the 32X is hard: the chip has no convenient debug port on the console, and emulators support it only partly. This page lists the ways the sources describe for debugging SH-2 code, how GDB stubs work and break, and what the SH7604 chip offers a debugger. Read it before you plan how to find a bug in code that runs on the SH-2s.

Summary#

  • The sources give three ways to debug SH-2 code.
    • GDB through an emulator. marsdev's skeleton names Gens-KMod, BlastEm and UMDKEMU[S061-1].
    • A GDB stub, a small agent running on the target that serves GDB's requests. Bill Gatliff describes how to write one in his article "Implementing a Remote Debugging Agent Using the GNU Debugger"COMM[S028-1][S028-who].
    • Hitachi in-circuit emulators (ICE) for the SH-2, in Sega's development tools overview dated 26 April 1994DOC[S006-1].
  • Two SH stubs are available.
    • sh-stub.c from the GDB source tree (the copy in Apple's gdb-309 release), "for the Hitachi-SH"CODE[S030-1].
    • The SH-2 port of gdbstubs, Bill Gatliff's stub collection on SourceForgeCODE[S029-who], tested on Hitachi's 7045EDK and 7043EDK boardsHW[S029-1].
    • Both were written for other boards. Their serial registers sit at $05FFFEC0CODE[S030-2] and $FFFF81A0CODE[S029-2]. The SH7604's serial port starts at H'FFFFFE00DOC[S003-1].
  • The 32X wiring gets in the way. The SH-2 serial port connects the master and the slaveDOC[S001-1], and NMI is tied highDOC[S001-2]. A stub therefore has no obvious serial line to a host computer (see Open questions).
  • Software breakpoints and steps write a TRAPA opcode over codeCOMM[S028-2]. So code in ROM cannot be stepped this way. gdbstubs says the same of flashCODE[S029-3]. The marsdev skeleton runs SH-2 .text from cartridge ROM (see Devkits (Chilly Willy's devkit, marsdev)).
  • Hardware breaks. The SH7604 has a user break controller (UBC) with two hardware break channels, meant for a self-monitoring debugger that needs no ICEDOC[S003-2].

Techniques#

  • Hardware step with the UBC. Set a channel to break on the next instruction's fetch and return.
    • Bill Gatliff's article shows this with SH704x UBC registersCOMM[S028-7].
    • The SH7604's own UBC registers are in the table above.
  • Software step: replace the next instruction with TRAPA #32 and restore it in the trap handlerCOMM[S028-8].

Pitfalls#

A step trap in a delay slot faults.

  • TRAPA is one of the instructions that rewrite the PCDOC[S003-14]. Such an instruction placed in a delay slot starts illegal slot exception handlingDOC[S003-15].
  • sh-stub.c has no case for BT/S, BF/S, BRAF or BSRF. Its decoder list ends at RTE and TRAPACODE[S030-13].
  • So stepping one of those puts the trap at the next address, which is the delay slot.
  • gdbstubs decodes them but marks BT/S and BF/S untestedCODE[S029-6].

UBC stepping has reported limits.

  • Bill Gatliff reports that some SH versions have a defective UBC that cannot step across instructions in delay slotsCOMM[S028-4].
  • His UBC step routine also fails when the next instruction is a TRAPCOMM[S028-5].

With an ICE attached, the UBC belongs to the ICE. None of the UBC functions are available to the programDOC[S003-16]. An ICE in trace mode also runs slower than the chip, so timing is measured on a real chipDOC[S003-17].

The stubs are written for another SH board and need porting.

  • sh-stub.c writes a bus control register it defines at $05FFFFA0CODE[S030-15].
  • The SH7604's bus control register 1 sits at $FFFFFFE0DOC[S003-bcr1].
  • A port must not simply retarget that write. The 32X manual tells applications not to access the SH-2 bus state controllerDOC[S001-3].

Do not compile TRAPA #32 into code debugged with gdbstubs.

  • The gdbstubs breakpoint handler always backs the stacked PC up by 2 to re-run the replaced instructionCODE[S029-20]. So a compiled-in TRAPA #32 loops forever.
  • The stub's own comment says to use TRAPA #33 for compiled-in breakpointsCODE[S029-21].

The reported SP needs the trap frame removed.

  • The SH-2 pushes PC and SR, four bytes each, on a trapCOMM[S028-6]. So a stub must correct the SP it reports to GDB.
  • sh-stub.c does it in saveRegisters: add #8, r15 ("hide PC/SR values on stack"), then it saves R15, then add #-8, r15CODE[S030-sp].

Video modes (packed pixel, direct colour, run-length)

The 32X can draw its picture in three pixel formats, plus a blank setting that hides the 32X layer. This page explains each format, how the bitmap mode register selects it, and how a mode change behaves from line to line. Read it to choose a format for your game and to find the register bits that set it from either CPU.

Summary#

  • Four modes from two bits. M1 and M0 of the bitmap mode register pick blank, packed pixel, direct colour or run-length for the 32X layerDOC[S001-2-modes].
  • Packed pixel: one byte per pixel, which is a palette indexDOC[S001-2-packed].
  • Direct colour: one 16-bit word per pixel, with 15 bits of colourDOC[S001-2-direct].
  • Run-length: one 16-bit word per run, holding 8 bits of pixel count and 8 bits of palette indexDOC[S001-2-rle].
  • Size. The picture is 320 x 224 or 320 x 240, non-interlaced onlyDOC[S001-2-size]. 240 lines are valid only in PALDOC[S001-2-240pal].
  • Timing. A mode change is accepted at any time and takes effect from the next lineDOC[S001-2-nextline].
  • No scaling or rotation hardware. Such effects are done in softwareCOMM[S012-2-norot].

Details#

Bitmap mode register#

This register is at $A15180 on the 68000 side and $20004100 (cache-through) on the SH-2 sideDOC[S001-2-bmaddr]DOC[S001-2-ctvdp]. Bits 14 to 8 and 5 to 2 are unused.

The layout is the one in Sega's 32X Hardware Manual, revision R4 (July 1994), page 36DOC[S005-2-bmbits]. The 32XDK copy of the manual prints PRI and 240 at other bit positions; see "Where sources disagree" below.

  • Released code uses the R4 layout. d32xr, the GitHub source of Doom 32X Resurrection (a homebrew rework of Doom for the 32X), sets PRI with 0x0080CODE[S097-2-pri] and 240 lines with 0x0040CODE[S097-2-240].
  • NTSC test. d32xr tests NTSC as bit 15 = 1CODE[S097-2-ntsc].

The VDP latches its registers once per line, so bitmap mode and screen shift settings apply from the next lineDOC[S001-2-latch].

  • A V-blank-only note under the PAL bit. The manual prints "Switching is possible only during V Blank" under the PAL bitDOC[S005-2-vbnote]DOC[S001-2-vbnote].
    • The PAL bit is read-only, so treat the 240 bit as switchable in V-blank only.

Colour word#

Direct colour pixels and palette entries share one 16-bit layout: a priority bit followed by three 5-bit colour fields.

BitsMeaningSource
15, 14-10through (priority) bit; blue, 5 bitsDOC[S001-2-cb]
9-5green, 5 bits, 1Fh brightestDOC[S001-2-cg]
4-0red, 5 bits, 1Fh brightestDOC[S001-2-cr]
  • The palette is a RAM block of 256 wordsDOC[S001-2-pal256].
  • Packed pixel and run-length data select colours from itDOC[S001-2-paluse].
  • Palette access rules are on Palette (CRAM) and priority.

Packed pixel (8 bpp)#

Packed pixel is the usual choice. Each byte of the frame buffer is an index into the 256-entry palette, so a line of 320 pixels takes 160 words.

  • One byte per pixel, each an index into the paletteDOC[S001-2-packedb]. The 32XDK wiki (the community-written wiki for 32X developers on GitHub) puts it the same way: each frame buffer byte is one palette entryCOMM[S012-2-packed].
  • Two pixels per word, 160 words per lineDOC[S001-2-160].
  • Byte order. Lusid Dreams is a Commodore 64 SID music player for the 32X, published on GitHub by mic in 2016. It writes pixel x of a packed line at byte offset x from the line start, so the byte at the lower address is the left pixelCODE[S087-2-px].
    • On the big-endian SH-2 the lower-address byte is the high byte, so the left pixel is the high byte of each wordDERIVED[S087-2-pxderiv].
    • The jgenesis emulator shows packed pixels the same way; see the emulator section below.
  • 408 lines of pixel data fit in one frame buffer after the line tableDOC[S001-2-408].
  • Line starts. Starts are word offsets, so a line can only start on a 2-pixel stepDOC[S001-2-2dot]. The screen shift bit gives the 1-pixel step for horizontal scrollingDOC[S001-2-sftwhy].
  • Word writes cannot go to odd byte addresses, so word-drawn 8-bit cells also land on 2-pixel stepsCOMM[S040-2-odd].

Direct colour (16 bpp)#

In direct colour every pixel carries its own colour, so no palette lookup happens. The price is capacity: a line takes 320 words.

  • One 16-bit word per pixel, 15 bits of colour (32,768 colours)DOC[S001-2-directb].
  • 320 words per lineDOC[S001-2-320w].
  • Only 204 lines can be displayed. More lines are possible by letting lines share identical line dataDOC[S001-2-204].
  • Bit 15 is the priority bit and bits 14 to 0 are BGR, 5 bits per componentCOMM[S012-2-bgr].
  • The palette is not used in this modeCOMM[S012-2-nocram].

Run-length#

In run-length mode a line is stored as a list of runs, each a count and a colour. Flat-shaded areas then cost very little memory.

Sega's manual documents the word and the clipping rule:

  • Each 16-bit word is one run: an 8-bit palette index and an 8-bit run lengthDOC[S001-2-rleb].
  • The through (priority) bits of the palette colours still apply in this modeDOC[S001-2-rlethru].
  • When a line's runs add up to more than 320 pixels, the first 320 are shown and the rest ignoredDOC[S001-2-rleclip].

The count is the high byte, and a count n draws n + 1 pixels. The manual does not say which byte holds the count, nor how a count maps to pixels; forum posts and the 32XDK wiki give the answer. Ketsuban, a Sega-16 forum member, says in the thread "32x graphics modes" (2010) that the first 8 bits are the pixel count and the second 8 bits the palette indexCOMM[S042-2-rleorder]. Chilly Willy notes in the Sonic Retro forum thread "32X framebuffer questions" that the SH-2 and the 32X hardware are big-endian, so the first byte in memory is the high byteCOMM[S043-2-be]. The 32XDK wiki likewise describes each entry as 2 bytes, a count plus a palette indexCOMM[S012-2-rle].

The n + 1 rule follows from two worked examples, each of which fills exactly one 320-pixel line:

  • In "32x graphics modes", Chilly Willy writes a whole line in one colour C as the two words 255:C and 63:CCOMM[S042-2-rleex]. (255 + 1) + (63 + 1) = 320, whereas 255 + 63 = 318 would leave the line shortDERIVED[S042-2-rlederiv].
  • ob1, a member of the GenDev forum, in the thread "Frame Buffer Switch" (2007), draws a 165-pixel red line from pixel 48 on black as 2F00h, A401h, 6A00hCOMM[S039-2-rle]. ($2F + 1) + ($A4 + 1) + ($6A + 1) = 48 + 165 + 107 = 320DERIVED[S039-2-rlederiv].

The 32XDK wiki suggests run-length for an engine built around flat polygons, and calls it "probably" faster than the other modes, since one write can fill a run instead of several writes per raster lineCOMM[S012-2-rlefast].

Setting a mode from the SH-2#

The sketch below sets packed pixel mode the way the start-up code of Lusid Dreams does it. It writes the mode register, then swaps buffers and writes the line table of each buffer in turnCODE[S087-2-init]CODE[S087-2-flip]. Its mode constants are the values defined in d32xr's 32x.hCODE[S097-2-modes]. The run-length line is Chilly Willy's one-colour example from the section above.

/* SH-2 side, cache-through. Mode values as in d32xr's 32x.h. */
#define VDP_MODE (*(volatile unsigned short *)0x20004100)
#define FB_CTL   (*(volatile unsigned short *)0x2000410A)
#define FB       ((volatile unsigned short *)0x24000000)

#define LINES_224 0x0000   /* bit 6 (240) = 0: 224 lines */
#define MODE_256  0x0001   /* M1 M0 = 0 1: packed pixel */
#define MODE_RLE  0x0003   /* M1 M0 = 1 1: run-length */
#define FB_FS     0x0001   /* FS: the buffer on display */

/* The SH-2 must own the VDP (FM = 1) before calling these. */

/* Swap buffers and wait until the swap has happened. */
static void flip(void)
{
    unsigned short shown = FB_CTL & FB_FS;

    FB_CTL = shown ^ 1;               /* swap at the next V-blank */
    while ((FB_CTL & FB_FS) == shown) /* FS reads the old buffer */
        ;                             /* until the swap is done */
}

/* Packed pixel, 224 lines, line i at word i x 160 + 0x100. */
void init_packed(void)
{
    int b, i;

    VDP_MODE = LINES_224 | MODE_256;
    for (b = 0; b < 2; b++) {         /* once for each buffer */
        flip();                       /* the other one is now ours */
        for (i = 0; i < 224; i++)
            FB[i] = i * 160 + 0x100;  /* word offset of line i */
    }
}

/* Run-length: a single stored line of two runs of colour c,
   shown on every display line. The count is the high byte and
   a count n draws n + 1 pixels, as the forum examples show. */
void init_rle_flat(unsigned char c)
{
    int i;

    FB[0x100] = (255 << 8) | c;       /* 255 + 1 = 256 pixels */
    FB[0x101] = (63 << 8) | c;        /* 63 + 1 = 64: 320 in all */
    for (i = 0; i < 224; i++)
        FB[i] = 0x100;                /* every line, same data */
    VDP_MODE = LINES_224 | MODE_RLE;
    flip();                           /* put it on display */
}

The mode register takes effect from the next line, so it can be written at any time. The line table, by contrast, belongs to one buffer, and after a swap the frame buffer address reaches the buffer that was on displayDOC[S001-2-anim]. That is why init_packed swaps before writing each table, as Lusid Dreams does. A packed line of 320 pixels takes 160 words, so line i starts 160 x i words after the 256-word table.

In init_rle_flat every line-table entry points at the same two words; the manual allows lines to share identical line dataDOC[S001-2-share]. The run-length byte order and the n + 1 rule in its comments come from the forum examples, not from Sega's manual.

Screen shift#

The screen shift register moves the whole 32X picture one dot to the left. It exists because line starts in the line table are word offsets, so lines can only be scrolled in steps of 2 pixels in packed pixel mode. The full page is Screen shift (1-pixel horizontal scroll).

  • The screen shift control register is at $A15182 on the 68000 side and $20004102 on the SH-2 sideDOC[S001-2-sftaddr].
  • Bit 0, SFT: 1 shifts the 32X picture 1 dot to the leftDOC[S001-2-sft].
  • It can be written at any time and applies from the next lineDOC[S001-2-sftline].
  • The manual's register table describes it as horizontal scroll for packed pixel modeDOC[S001-2-sftpp]. The 32XDK wiki gives the same address and behaviourCOMM[S012-2-sft].
  • Scrolling recipe. Set the line-table entries to vertical scroll plus (horizontal scroll & ~1), then set SFT to horizontal scroll & 1. Redo it every frameCOMM[S044-2-scroll].
  • Limit. SFT has no effect on a line whose line-table entry has $FF as its low byte. Keep that byte off $FF when using shift (Sega Technical Bulletin 14)DOC[S070-2-tb14]. The 32XDK wiki relays the same precautionCOMM[S009-2-tb14].

Resolution, lines and the Mega Drive mode#

  • When the 32X layer is not blank, the Mega Drive VDP must run at the same resolution as the 32XDOC[S001-2-mdres].
  • 320 x 240 on the 32X pairs with the Mega Drive's 40 x 30 cell modeDOC[S001-2-mdh40].
  • Setting the 240 bit in NTSC makes the VDP malfunctionDOC[S001-2-ntsc240].
  • The 32XDK wiki sums it up as NTSC 224 lines at 60 HzCOMM[S012-2-ntsc] and PAL 240 lines at 50 HzCOMM[S012-2-pal]. PAL can also run 224 lines.

Bandwidth#

The manual gives the per-write cost: 3 clocks, or 5 with the FIFO full (see Frame buffer and line table). Two members of the GenDev forum turned that cost into a frame budget in the thread "Super VDP" (2009).

Snake, who writes there that he worked with this hardware a lot in the past, says that writing the frame buffer non-stop passes one write every 5 cycles at bestCOMM[S038-2-5cyc]. That caps a frame at about 76,000 writes, roughly one 320 x 224 layer drawn with byte writesCOMM[S038-2-76k]. Chilly Willy reads the manual the same way: a write enters the FIFO in 3 cycles while it has room, and the FIFO drains no faster than one write every 5COMM[S038-2-fifo]. With word writes Chilly Willy counts about 32,000 writes for a full 256-colour frame and 64,000 for a 15-bit oneCOMM[S038-2-32k].

Snake found no clear gain from writing in V-blankCOMM[S038-2-vbl], and found DMA into the frame buffer no faster than the CPUCOMM[S038-2-dma]. Snake's way to reach the 5-cycle limit is to write from both SH-2s, so that one fetches its next pixel while the other waits on the FIFOCOMM[S038-2-both]. How to write at the cap is on Wide frame-buffer writes.

Techniques#

  • Per-line changes. Modes, priority and screen shift apply per line (see the bitmap mode register above).
  • Mid-screen mode switch. Sega's own Mars Check program does it from the 68000.
    • In its "3 MODE DISPLAY" test the Mega Drive VDP's H interrupt counts lines.
    • The 68000 writes the bitmap mode byte at lines $10, $50, $90 and $D0 with $81, $82, $83 and $80 (packed pixel, direct colour, run-length, blank, PRI set in all four)CODE[S206-2-mid][S206-2-lines].
    • TascoDLX, another GenDev forum member, reports in the thread "Mars Check Program results for Kega Fusion v3.61" (2009) that all of the program's tests have been reported to succeed on real hardwareCOMM[S115-2-mcpass].
    • Kega Fusion 3.61 showed no 32X display during that testEMU[S115-2-fusion].
  • Run-length suits flat-shaded polygons (see the section above).

Pitfalls#

The shift bit does not work on $xxFF line starts. SFT is ignored on lines whose line-table entry ends in $FFDOC[S070-2-tb14]. The jgenesis emulator models it; see the emulator section below. What to do: keep the entry's low byte off $FF.

240 lines on NTSC makes the VDP malfunctionDOC[S001-2-ntsc240]. Set the 240 bit only after reading PAL = 0.

  • Sega's Mars Check program keeps a copy of the Mega Drive version register $A10001.
  • Before a display test it writes $42 (240 lines) to the bitmap mode register's low byte only when that copy's bit 6 is set, otherwise $02 (224 lines)CODE[S201-240pal].
  • Bit 6 of $A10001 is 1 on PAL unitsDOC[S094-2-pal].

Direct colour cannot cover 224 unique lines in one frame buffer (204 fit). Repeat lines through the line table, or use a shorter picture.

  • The direct-colour set-up of 32x-playground, gameblabla's 32X repository on GitHub, does exactly that: 200 unique lines, and every entry after them points at line 200CODE[S057-2-200].

32X and Mega Drive pixels do not line up exactly. Sega's bulletin "32X Hardware Information" gives the 32X dot offset against the Mega Drive picture as up to 1/2 dot left or right on production unitsDOC[S002-2-dot]. Mixing is on Mixing the 32X picture with the Mega Drive VDP.

Tested on the jgenesis emulator#

jgenesis is an open-source Mega Drive and 32X emulator (Emulators and their 32X accuracy). These results come from test ROMs run on its version 0.14.1, and nobody has confirmed them on a real 32X yet.

  • Packed byte order. The high byte of each word is the left pixel. In a line of unequal-byte words, the high byte is shown firstEMU:jgenesis core 0.14.1[T201-2-order].
  • Shift bit on $xxFF lines. With SFT = 1 a $80FF line stays put while a $8100 line shiftsEMU:jgenesis core 0.14.1[T207-2-ff].
  • The 240 bit on NTSC. The emulator keeps the bit as written but goes on showing a normal 224-line picture, with no fault where the manual warns of VDP operating errorsEMU:jgenesis core 0.14.1[T217-ntsc]. A program that sets the bit on NTSC can therefore look fine on jgenesis and still misbehave on a console.

Where sources disagree#

Disagreements on every topic are collected on where sources disagree.

240 lines on NTSC: VDP errors, or nothing visible?

  • The 32XDK copy of the manual says setting the 240 bit in NTSC makes the VDP malfunctionDOC[S001-2-ntsc240].
  • The jgenesis emulator shows no visible fault. Do not set 240 on NTSC.

Bit positions of PRI and 240.

  • Sega's R4 manual (July 1994), page 36, puts PRI at bit 7 and 240 at bit 6DOC[S005-2-bmbits].
  • The 32XDK copy of the manual puts PRI at bit 13 and 240 at bit 7DOC[S001-2-bmbits].
  • Use the R4 positions. d32xr sets PRI with 0x0080 and 240 lines with 0x0040CODE[S097-2-pri]CODE[S097-2-240].

Open questions#

  • On a real 32X, is the run-length count the high byte of the word, and does a count n draw n + 1 pixels, as the forum examples imply?
  • Which bit does the manual's "only during V Blank" note under the PAL bit refer to?

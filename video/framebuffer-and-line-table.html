Frame buffer and line table

The 32X draws its picture from two frame buffers. This page explains how a frame buffer is organised, how the line table inside it chooses what each display line shows, who may touch the buffer at a given moment, and how to flip and clear buffers safely. Read it before you write any code that draws pixels, because most 32X display bugs come from breaking one of these access rules.

Summary#

  • Two frame buffers. Each is 1 Mbit of DRAM. One is on display while the CPUs draw into the otherDOC[S001-fb2x]. The 32XDK wiki (the community-written wiki for 32X developers on GitHub) gives the same size as 128 KB eachCOMM[S012-128k].
  • A line table comes first. Each frame buffer starts with a line table of 256 wordsDOC[S001-lt256]. Each entry points at the pixel data of one display lineDOC[S001-ltaddr]. The entry is a word offset, not a byte offsetCOMM[S012-wordoff].
  • FS picks the displayed buffer. A write during active display takes effect at the next V-blankDOC[S001-fsnext].
  • FM decides who may touch the buffer. The 68000 needs FM = 0DOC[S001-fm68k]. The SH-2s need FM = 1DOC[S001-fmsh2].
  • Zero bytes are ignored. A byte write of 00h to the frame buffer does nothingDOC[S001-zb]. A word write of 0000h is storedDOC[S002-zw].

Details#

For the VDP as a whole, start at 32X VDP overview.

  • The 32XDK wiki's bugs page adds a mirror of the overwrite image at $24060000-$24080000, which it marks as uncertainCOMM[S009-mirror].
  • fedex81, the author of the helios32x emulator, reports in issue 744 of the ares emulator on GitHub (2023) that adding the DRAM mirror made Soulstar X show its missing 32X layerEMU[S083-mirror].
  • The jgenesis emulator models both mirrors; see the emulator section below.

Layout inside one frame buffer#

Offsets below are from the base of the buffer.

  • Line table first. Sega's drawing puts the line table first, with pixel data starting at offset $00200DOC[S002-layout].
  • A second window. The same drawing labels $20000 to $3FFFF "Frame Buffer Image"DOC[S002-layout2].
  • Where lines may start. The 32XDK wiki says lines should start at word 256 or higherCOMM[S012-w256].
  • Word 256 in bytes. That is byte offset $00200, since 256 x 2 bytes = 512 = $200DERIVED[S012-w256].

Line table#

The line table is what makes the 32X flexible. The VDP does not assume that line n sits n x 320 pixels into the buffer. It reads the table instead, so lines can be reordered, repeated or scrolled.

  • Size. The line table is the first 256 words of the frame bufferDOC[S001-lt256b].
  • What an entry does. It holds the location of one line's pixel data. Writing it selects what that line showsDOC[S001-ltaddrb].
  • Units. The entry is a word offset into the frame buffer, not a byte offsetCOMM[S012-wordoffb].
  • Entries used. Only the first 240 are used, because 240 is the most lines the VDP outputs (PAL)COMM[S012-240].
  • Released code, example 1. Lusid Dreams, mic's SID music player for the 32X, fills entry i with i x 160 + 0x100. That is word offsets: 160 words per packed line, first line at word 256CODE[S087-lt].
  • Released code, example 2. d32xr (Doom 32X Resurrection) fills entry j with j x 320 / 2 + 0x100. It points every remaining entry at one blank lineCODE[S097-lt].
  • Scratch words. d32xr uses the table's 16 unused words (entries 240 to 255) as scratch storage. That fits with only 240 entries being readCODE[S097-unused].
  • Line length. The VDP reads 320 pixels from the entry's address, whatever follows itDOC[S001-320px].
  • Running off the end. If fewer than 320 pixels of DRAM follow the address, the overwrite-image area is displayed as pixel dataDOC[S001-owshown]. Sega's bulletin "32X Hardware Information" gives the same warning for lines whose 320 dots do not fit in the frame bufferDOC[S002-320warn].
  • Start steps. Entries are word offsets, so packed-pixel lines can only start on 2-pixel stepsDOC[S001-2dot].
    • The 32XDK wiki describes the same limit as scrolling 256-colour pixels two at a timeCOMM[S012-2px].
    • The screen shift bit (SFT) gives the missing 1-pixel step; see Video modes (packed pixel, direct colour, run-length)DOC[S001-sft].

Capacity per frame buffer#

The numbers are the manual's own arithmetic (bpp = bits per pixel). Several lines may point at the same data, which raises the line countDOC[S001-share]. After the 256-word table, a 16-bit line takes 320 words and an 8-bit line takes 160 words, so fewer 16-bit lines fit.

Frame buffer control register#

This register sits at $A1518A on the 68000 side and $2000410A (cache-through) on the SH-2 sideDOC[S001-fbcaddr]. Most of it reports status. Only FS can be written.

Bit15141312-210
FieldVBLKHBLKPEN-FENFS
Accessread onlyread onlyread only-read onlyread/write

The bit layout and access are given by the manualDOC[S001-fbcbits].

  • VBLK is 1 during vertical blankDOC[S001-vblk].
  • HBLK is 1 during horizontal blankDOC[S001-hblk].
  • PEN is palette access approvalDOC[S001-pen]. The palette is described on Palette (CRAM) and priority.
  • FEN = 1 means frame buffer access is denied because a fill is runningDOC[S001-fen].
  • FS = 0 sends DRAM0 to the display (initial value). FS = 1 sends DRAM1DOC[S001-fs].

Swapping buffers (FS)#

  • The swap itself happens during V-blank (VBLK = 1) or in blank modeDOC[S001-swapwhen].
  • FS may be written at any time. Written during display, the swap waits for the next V-blankDOC[S001-fsnextb].
  • Until that V-blank, reading FS returns the buffer still on displayDOC[S001-fsread].
  • After requesting a swap, touch the frame buffer only once VBLK = 1 or the FS read-back has changedDOC[S001-fswait].
  • Lusid Dreams does exactly this: write FS, then wait until the FS read-back changesCODE[S087-fs].

The buffer that was on display is then mapped for drawing, so a game can draw one frame while the other is shownDOC[S001-anim].

The swap routine below is d32xr's, from its marshw.c, with the register address and FS bit of its 32x.h written outCODE[S097-flip]CODE[S097-fsmask]. It runs on the SH-2, which must hold FM = 1. d32xr reaches its record of the active buffer through a cache-through addressCODE[S097-active].

#define FB_CTL (*(volatile unsigned short *)0x2000410A)
#define FB_FS  0x0001        /* bit 0: the buffer on display */

/* The buffer last asked for. d32xr keeps this word at a
   cache-through address, so no read comes from a stale cache. */
static volatile unsigned short active;

/* Has the swap asked for last taken place yet? */
int frame_buffers_flipped(void)
{
    return (FB_CTL & FB_FS) == active;
}

/* Ask for the other buffer; with wait set, return only once it
   is on display and the old one is free for drawing. */
void flip_frame_buffers(int wait)
{
    active = !active;        /* the other buffer */
    FB_CTL = active;         /* written mid-frame: done at V-blank */
    if (wait)
        while (!frame_buffers_flipped())
            ;                /* FS reads the old buffer until then */
}

The mask matters, because the status bits VBLK, HBLK, PEN and FEN share the register with FS. With wait = 0 the SH-2 can do work that does not touch the frame buffer, such as game logic, and call frame_buffers_flipped before it draws again. The buffer it then draws into still holds the frame from two frames ago; the pitfall "A swap does not clear anything" below says how to deal with it.

Access rules#

The same rules, ordered by time of the frame, are on V-blank and H-blank access rules.

  • 68000. It may access the frame buffer, overwrite image, VDP registers and palette only when FM = 0DOC[S001-fm68kb].
  • SH-2s. They may access the same blocks only when FM = 1DOC[S001-fmsh2b].
  • Wrong side. On the 68000 side with FM = 1, reads are undefined and writes are ignoredDOC[S001-fmwrong].
  • Byte writes. They work, except that a byte of 00h is ignored. This holds for the 68000 and the SH-2 alikeDOC[S001-zbb].
  • Which values can be written. Bytes 01h to FFh can be written, and so can a word of 0000hDOC[S002-zwb].
  • The 32XDK wiki's version. Zero bytes are ignored and zero words are storedCOMM[S012-zero].
  • Z80. The manual's register access table marks the frame buffer as reachable from the Z80DOC[S001-z80].

Overwrite image#

The overwrite image exists to make transparent pixels cheap: a write through it skips every byte that is zero, so a sprite can be written over a background without reading the background first.

  • Same RAM. It is the same physical RAM as the frame buffer DRAM, reached through another address rangeDOC[S001-owsame].
  • Byte writes. A byte of 00h written there leaves the frame buffer byte unchangedDOC[S001-ow00].
  • Word writes. Whichever byte is 00h is left unchanged, and the other byte is writtenDOC[S001-owword].
  • The 32XDK wiki's summary. Zero bytes and zero words are ignored, and this also holds in direct colour modeCOMM[S012-owdirect].

Timing#

A wait is one clock added to the CPU's minimum bus cycleDOC[S001-waitdef]. That minimum is 4 clocks on the 68000 and 2 on the SH-2DOC[S001-buscyc].

CPUAccessWait statesSource
SH-2read5 (min) to 12 (max)DOC[S001-shr]
SH-2write1 (min) to 3 (max)DOC[S001-shw]
68000read2 (min) to 4 (max)DOC[S001-68r]
68000write0DOC[S001-68w]
  • Write FIFO. SH-2 writes go through a 4-word FIFODOC[S001-fifo4].
    • A write takes 3 clocks while the FIFO has roomDOC[S001-fifo3].
    • It takes 5 clocks when writing 4 words or more back to backDOC[S001-fifo5].
  • Idle cycles. They are absorbed, but no access takes less than 3 clocksDOC[S001-idle].
  • Bytes cost as much as words. Writing pixels one byte at a time halves the bandwidthCOMM[S040-bytecost].
  • Best burst. With four FIFO slots, bursts of 4 words (8 bytes) suit the frame buffer bestCOMM[S040-4words].
  • Two hardware versions. Sega's bulletin "32X Hardware Information" calls them "Target Ver. 1.0" and "Ver. 2.0".
    • Frame buffer reads take 9 and 7 clocks (min)DOC[S002-rdver].
    • Sustained writes take 7 and 5 clocks (min)DOC[S002-wrver].
  • FEN during refresh. FEN is also 1 while the VDP refreshes its DRAM, yet DRAM access is allowed thenDOC[S001-fenrefresh]. That refresh pulse is 40 SH-2 clocks wideDOC[S001-fenwidth].

Techniques#

Most of these come from two GenDev forum threads: "Shamefully noob question about 32x framebuffer sizes" (2013), with posts by Charles MacDonald and Chilly Willy, and "Optimizing background tiles drawn to framebuffer" (2012), with posts by Chilly Willy.

  • The line table is worth using. Toshiyasu Morita's "Programming the 32x FAQ", copied on the "Optimizations" page of the 32XDK wiki, lists the scanline start table and run-length mode among the useful 32X hardwareCOMM[S010-hw].
  • Repeat lines to save memory or drawing time. Point several line-table entries at the same line of pixels; the capacity note under the line table explains why this raises the line count.
  • Draw at half height. Point each pair of line-table entries at the same line of pixels and draw only 112 lines for a 224-line screen. Chilly Willy reports in the GenDev thread "Questions about drawing on 32X" (2014) that his Yeti3D demo does this, and that it really sped up drawingCOMM[S035-yeti].
  • Scroll a canvas bigger than the screen. Draw an 8-bit picture wider or taller than 320 x 224 into the buffer, and move the 320 x 224 window by rewriting the line table each frame. Charles MacDonald sizes such a canvas at 512 x 256COMM[S041-512], and Chilly Willy at 640 x 224COMM[S040-640].
    • Neither size quite fits. 512 x 256 is 131,072 bytes, the whole buffer, so with the 512-byte line table in front only 255 lines of 512 fit. 640 x 224 is 143,360 bytes, so only 204 lines of 640 fit in the 130,560 bytes after the tableDERIVED[S001-canvas].
  • Rotate four screens. In 8-bit mode each frame buffer holds two 320 x 204 screens, so four screens can rotate through the two buffersCOMM[S041-four].
  • Direct colour at 320 x 200. Point the first 200 entries at the picture and the last 40 at one blank lineCOMM[S041-200]. A direct-colour picture has to be letterboxed to 320 x 204 or lessCOMM[S041-letterbox].
  • Draw sprites through the overwrite image. Pad the sprite with zero pixels and write it whole through the overwrite window. The zero pixels leave the background alone, so no read-modify-write is neededCOMM[S041-sprite].
  • Overdraw margins instead of clipping. Widen the buffer by 4 words on each side (336 x 224), draw sprites without clipping them at the screen edge, and let the line table show only the 320-pixel windowCOMM[S040-336]COMM[S040-320].
  • Use the spare frame buffer RAM. A 320 x 240 8-bit picture leaves about 53 KB of each frame buffer free, which Chilly Willy suggests for tile dataCOMM[S041-53k].

Write-speed techniques are on Wide frame-buffer writes.

Pitfalls#

FM ownership can change under a running access.

  • While the SH-2 side holds FM = 1, a 68000 access is forcibly interrupted, and what follows is not guaranteedDOC[S001-fmforce].
  • What to do: hand FM over only when the other side is idle.
  • d32xr is the GitHub source of Doom 32X Resurrection, a homebrew rework of Doom for the 32X. Its SH-2 posts a command in communication word 0 and spins until the 68000 clears itCODE[S097-q-hand].
  • The 68000 drops FM only inside that command, reads the frame buffer, then gives FM backCODE[S088-q-fm].

FM = 0 straight after SH-2 frame buffer writes can lock up the machine.

  • Sega's 32X Hardware Manual Supplement 1 (June 1994) warns about this. If the SH-2 hands FM back while the interface is still writing buffered data, the SH-2, the 68000 and the VDP can all lock upDOC[S005-sup-lock].
  • The remedy: before switching FM, read the frame buffer, a VDP register or the palette, or write a VDP register or the palette. That lets the buffered data go throughDOC[S005-sup-fix].
  • In d32xr's 68000 command handler, the 68000 unsets FM with a write of $A15100 after toggling bit 15 of the registerCODE[S088-q-after].

An SH-2 access while FM = 0: ignored, or held until FM = 1? The manual says both. Its section 3.1 says such writes are ignored, while its section 3.4 says the access waits until FM = 1; see "Where sources disagree" below.

  • The jgenesis emulator drops the write and does not hold the SH-2 until FM = 1; see the emulator section below.
  • Lusid Dreams stays clear of the question: it waits until the SH-2 holds FM before any VDP accessCODE[S087-q-wait].

Lines near the end of the buffer.

  • A line whose entry leaves fewer than 320 pixels of DRAM shows overwrite-image data (see the line table above). Sega's original manual gives this as a display precautionDOC[S005-overrun].
  • The jgenesis emulator's result is in the section below.

A swap does not clear anything.

  • The buffer handed back for drawing still holds the frame drawn two frames ago. Fonzie, answering ob1 in the GenDev forum thread "Frame Buffer Switch" (2007), confirms that it still has its dataCOMM[S039-old].
  • Lusid Dreams clears each buffer itself after flipping to itCODE[S087-q-clear].

Zero bytes matter in practice.

  • djcouchycouch, who asked the questions in the GenDev forum thread "Questions about drawing on 32X" (2014), reports there that testing confirms the zero-byte ruleCOMM[S035-tested].
  • Chilly Willy says in the GenDev thread "Shamefully noob question about 32x framebuffer sizes" (2013) that the rule caused him trouble when he started Wolf32XCOMM[S041-wolf].
  • notaz, the author of the PicoDrive emulator, adds in the GenDev thread "Super VDP" (2010) that several games even rely on the zero-byte skipCOMM[S036-notaz].
  • d32xr works around it. To end a string it builds in the frame buffer, it writes the zero as a 16-bit word and then puts back the byte beside itCODE[S097-q-zero].

SH-2 DMA into the frame buffer: Sega's own test program uses it. Forum posts disagree on whether it is allowed; see "Where sources disagree" below.

  • Sega's Mars Check test program, part of Sega's 32X SDK, does it. Two of its SH-2 routines load DMAC channel 0 with DAR0 = $24000000 (the frame buffer, cache-through) and CHCR0 = $5EE1 (auto-request, 16-byte unit). They then compare the frame buffer with the source word by wordCODE[S205-dmafb].
  • TascoDLX, a member of the GenDev forum, reports in the thread "Mars Check Program results for Kega Fusion v3.61" (2009) that all 161 of the program's tests have been reported to succeed on real hardwareCOMM[S115-mcpass]. That report covers its DMA tests and the fill tests described below.
  • Sega's R4 manual's DMA page allows auto-request transfers between memories within the SH-2 address space and does not mention the frame bufferDOC[S005-dmaauto].
  • Do not expect a speed-up. Snake, who writes in the GenDev forum thread "Super VDP" (2009) that he worked with this hardware a lot in the past, finds DMA into the frame buffer no faster than the CPUCOMM[S038-dmaslow].

Clearing with 00h bytes does nothing.

  • Clear with word writes, or with auto fill (Auto fill (VDP frame buffer fill)).
  • Lusid Dreams clears with 16-bit writes of zeroCODE[S087-q-wclear].

After an auto fill, wait for FEN = 0 before touching the frame bufferDOC[S001-fenwait].

  • While the fill runs, VDP and SH-2 DRAM accesses collide, so the SH-2 must not access DRAMDOC[S001-fillnoacc].
  • The 32XDK bugs page spells it out. Only one SH-2 may use the filler, and neither SH-2 may touch DRAM until the fill endsCOMM[S009-fill].
  • Sega's Mars Check test program keeps this rule. After writing the fill length, address and data, it loops on FEN until it reads 0. Only then does it read the frame buffer back or start the next fillCODE[S102-poll].

Cached or cache-through?

  • The manual's VDP chapter says access "without the color palette is only a cache-through address"DOC[S001-ctonly]. Its SH-2 map also lists a cached address for the frame buffer.
  • Chilly Willy's answer in the Sonic Retro forum thread "32X framebuffer questions" covers writes. They reach memory through the cached address because the SH-2 cache is write-through, but they fill the cache. So write large buffers cache-throughCOMM[S043-wt].
  • Registers must be read cache-through, because a second read of a cached address comes from the cacheCOMM[S043-regs].
  • In the GenDev thread "Optimizing background tiles drawn to framebuffer", Chilly Willy's rule is to use the frame buffer and overwrite image uncachedCOMM[S040-uncached].
  • d32xr addresses both through the cache-through rangeCODE[S097-q-ct].

Reading FS back.

  • The read value is the buffer on display until the next V-blank. The status bits share the register, so mask to bits 1 and 0 or read the low byte before comparingCOMM[S043-fsmask].
  • d32xr masks with the FS bit and spins until it matches the buffer it asked forCODE[S097-fsmask].

Tested on the jgenesis emulator#

jgenesis is an open-source Mega Drive and 32X emulator (Emulators and their 32X accuracy). These results come from test ROMs run on its version 0.14.1, and nobody has confirmed them on a real 32X yet. Where jgenesis and a console may differ, code should follow the manual's rule rather than the emulator.

  • SH-2 write with FM = 0. The write is dropped, and the SH-2 is not held until FM = 1, which is the reading of the manual's section 3.1EMU:jgenesis core 0.14.1[T001-fm0]EMU:jgenesis core 0.14.1[T001-comm]. A very short stall would look the same in this test.
  • Line overrun. A line whose entry is $FFF8 shows 16 pixels, then wraps to DRAM word 0 and shows the line table as pixels, high byte of each word firstEMU:jgenesis core 0.14.1[T201-wrap].
  • SH-2 DMA into the frame buffer. A 64-word auto-request DMA lands all 64 words and sets TEEMU:jgenesis core 0.14.1[T202-lands].
    • Copying 2 x 16384 words took 44 watchdog counts by DMA against 72 by CPU, so on jgenesis DMA is the faster copyEMU:jgenesis core 0.14.1[T204-time]. That disagrees with Snake's report, so measure on a console before choosing DMA for speed.
  • FEN after a fill. FEN reads 1 right after the fill starts. An SH-2 write made during the fill survives, so jgenesis does not reproduce the collision the manual warns ofEMU:jgenesis core 0.14.1[T203-fen].
  • Mirrors. $24040000 reads back the frame buffer DRAM. $24060000 behaves like the overwrite image: a zero byte written through it leaves the DRAM byte unchangedEMU:jgenesis core 0.14.1[T205-mir].
  • Cached reads. A cached frame-buffer read returns stale data until the cache line is purged, as SDRAM doesEMU:jgenesis core 0.14.1[T206-cache].

Where sources disagree#

Disagreements on every topic are collected on where sources disagree.

SH-2 access to the video side while FM = 0.

  • Section 3.1 of the 32XDK copy of the manual says that while FM = 0, SH-2 reads are undefined and writes are ignoredDOC[S001-sh2fm0].
  • Section 3.4 of the same manual says the SH-2 access waits until FM = 1DOC[S001-sh2wait].

SH-2 DMA to the frame buffer.

  • Chilly Willy, in the GenDev thread "Super VDP" (2009), relays that Sega's documents forbid SH-2 DMA to the frame bufferCOMM[S036-nodma].
  • Snake, in the same thread, says it works but is no faster than the CPUCOMM[S038-dmaslow].
  • Neither Sega's R4 manual nor the 32XDK copy states a ban, and Sega's Mars Check test program uses it (see Pitfalls).
